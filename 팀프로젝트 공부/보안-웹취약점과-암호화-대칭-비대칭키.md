## 대표 보안 문제

### XSS (Cross-Site Scripting)
- 해커가 웹사이트에 악성 JS **코드를 심어 놓은 거**
  - 유저가 해커가 심어 놓은 코드가 있는 사이트를 누르면<br>코드가 유저의 쿠키에 있는 JWT 토큰을 읽어서 해커 서버로 가는 거
- 해결책
  - HttpOnly 쿠키 사용
    - JS로 쿠키를 조회하는 것이 차단됨

### CSRF (Cross-Site Request Forgery)
- 쿠키의 자동 배달 기능을 악용해 강제로 심부름을 시키는 공격
  - 유저가 로그인된 상황 + 브라우저 쿠키에 인증 정보가 존재
  - 유저가 악성 링크를 누르면 브라우저가 로그인한 서비스 서버로 들어가서 나쁜 코드를 실행<br>(100만원을 해커 계좌로)
  - 이 때 브라우저가 알아서 쿠키+인증정보를 붙여서 보냄
- 해결책
  - **SameSite 쿠키 속성**

<details>
<summary>SameSite / origin · site / CORS 상세 정리</summary>

- **origin** : scheme(http/https) + host + port<br>하나라도 다르면 다른 origin
- **site** = scheme + eTLD+1
  - **[eTLD 관련]**
    - **eTLD** : `.com`, `.co.kr` 등
    - **eTLD+1** : eTLD에다가 한 단계 더 붙인 거
- **same-origin** : scheme·host·port가 완전히 같음
- **same-site** : scheme + eTLD+1이 같음 (host 일부가 달라도 됨)
- **cross-site** : eTLD+1(또는 scheme)이 다름
  - 쿠키는 site 기준으로 동작

**CORS · 쿠키 · SameSite**
- 브라우저는 기본적으로 **한 origin의 스크립트가 다른 origin의 응답을 읽지 못하게** 막음
- 해결책 : CORS
  - 헤더(`Access-Control-Allow-Origin`)를 사용
  - 즉 Origin이 다를 때 풀어주는 방법 (쿠키랑은 상관 없다)
- **SameSite 쿠키**
  - `SameSite=Strict`
    - 무조건 같은 사이트 안에서 이동할 때만 쿠키 보내기
    - CSRF 공격을 100% 방어
    - 타 사이트에서 들어오면 UX가 망가짐
  - `SameSite=Lax`
    - 기본적으론 방어, 단 사용자가 직접 링크를 클릭해서 넘어오면 쿠키 보내기
    - CSRF 공격을 방어
    - 정상 링크를 타고 들어와도 로그인 상태 유지
  - `SameSite=None`
    - 사이트 상관없이 요청만 보내면 쿠키 쏘기
    - `Secure`(HTTPS 필수) 속성과 세트로 사용 필수

</details>

  - **CSRF 토큰 사용**
    - 서버가 요청 폼을 줄 때마다 일회용 비번을 같이 주고, 요청 때마다 토큰을 확인

## 데이터 암호화

- 암호화해 놓으면 유출되어도 대응 시간을 벌 수 있다

### 단방향 암호화 (SHA-256, MD5, BCrypt 등)
- 복호화 불가한 방식
- 암호화할 때 문자열을 바이트화 시키고 알고리즘을 돌리는 방식 (해시 사용)
- 이후 저장소에 넣을 때는 16진수 혹은 Base64 표기법을 사용해서 문자열로 표현한다
- **충돌 저항성**
  - 동일한 해시 값을 갖는 서로 다른 데이터를 찾기 어려울 때 충돌 저항성이 높다
    - 즉, 지문이 같은 사람이 없는 상황일 때 "충돌 저항성이 높다"라고 표현
  - 해시 알고리즘 : 서로 다른 데이터에 대해 최대한 다른 해시 값을 생성 (길이 제한 때문에)
- 비밀번호를 알려주는 기능은 못 함 → 초기화 하는 방향으로 ㄱㄱ
- **Salt (중요) — 보안 강화하기**
  - 같은 해시 알고리즘 사용 시 같은 데이터를 넣으면 항상 동일한 해시 값이 생성
    - 해시 값이 유출되면 원본도 위험
    - **레인보우 테이블** : 해커가 해시 값을 미리 계산해서 만들어 놓은 표
      - 해시 값 유출 시 원본도 위험
  - **[해결책] Salt 사용하기**
    - 솔트 = 임의의 값. 즉, 솔트 값에 따라 해시 값이 달라짐
    - 유출이 되어도 레인보우 테이블 보고 해킹하기 어려움
    - 사용자마다 다른 솔트를 이용한다면? 보안 강도를 엄청 높일 수 있다

### 양방향 암호화 (SSH 프로토콜, HTTPS 등 보안이 중요한 송수신에 주로 사용)
- 암호화·복호화 모두 가능한 방식 (AES, RSA) — 바이트 데이터 대상
- 복호화 시 키를 사용 ⇒ 같은 알고리즘·데이터라도 키에 따라 결과가 달라짐
  - **대칭키**
    - 암호화·복호화 할 때 각각 **같은 키** 사용
      - 키가 뚫리면 재앙
  - **비대칭 키**
    - 암호화·복호화할 때 **서로 다른 키** 사용
      - 공개 키 : 아무나 접근 (암호화 시 사용)
      - 개인 키 : 소유자만 접근 (복호화 시 사용)
      - 거꾸로 사용할 수도 있다
        - 개인 키로 암호화 (e.g. 인증 목적, SSH가 대표적)
    - 키 소유자가 키 2개를 생성하고 송신자에게 공개 키 전달
