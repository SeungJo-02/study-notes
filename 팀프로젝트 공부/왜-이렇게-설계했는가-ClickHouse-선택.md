## 1. 핵심 결정: 왜 ClickHouse인가 (3안 비교)

우리 서비스의 핵심 기능(**알람 · 시스템 메트릭 · 히트맵 · 드래그 선택**)은 **모두 집계 데이터**를 필요로 한다. 그래서 "집계를 얼마나 쉽게 하느냐"가 저장소 선택의 축이 됐다.

| 기준 | HBase + Flink | Cassandra + Flink | **ClickHouse (선택)** |
|---|---|---|---|
| 강점 | 강한 일관성 · 단일조회+범위스캔 · 하둡 생태계 통합 | **수평 확장성·고가용성 최고**(마스터리스) | **OLAP — 쿼리 하나로 집계** |
| 집계 | 못함 → Flink가 대신(미리 질의 알아야 함) | 못함 → Flink 필요 | **DB 자체가 집계**(MV로 자동) |
| 운영 부담 | **매우 무거움**(HDFS·ZooKeeper·HMaster·RegionServer…) | Flink 인프라·쿼리 드리븐 모델링 부담 | **가벼움**(테이블 추가 불필요) |
| 고가용성 | 컴포넌트 多 → 장애지점 多 | **최고** | 카산드라보다 낮음(→ 복제로 보완) |
| 조회 속도 | 빠름 | 보통 | 단건은 느림, **집계는 빠름** |

### 1-1. HBase + Flink — 왜 뺐나
- **장점**: 강한 일관성(누가 언제 읽어도 동일), 단일 조회 + 범위 스캔 모두 가능(카산드라는 파티션 벗어난 범위 스캔이 힘듦), 하둡 생태계(HDFS 무한 저장소 등) 통합. **Pinpoint가 쓰는 방식**.
- **결정적 단점**: **무겁고 복잡한 아키텍처**. HBase 하나 띄우려면 `HDFS`·`ZooKeeper`·`HMaster`·`RegionServer` 등 컴포넌트가 너무 많아 **인프라가 무겁고 유지보수가 헬**. 컴포넌트가 많으니 **장애지점↑(가용성↓)**, 멀티 리전 Active-Active도 어렵다(카산드라는 설정 딸깍).
- 집계도 카산드라보다 약해 Flink가 대신하는데, **Flink는 미리 질의를 알아야** 집계 가능 → **히트맵**에서 걸린다.
- 정리: **정합성·고가용성을 챙기고 집계 유연성·운영 단순함을 버리는** 선택.

### 1-2. Cassandra + Flink — 왜 뺐나
- **장점**: **수평 확장성·고가용성이 가장 뛰어남**. 마스터리스라 마스터가 죽어도 재선출 시간이 필요 없다. 일관된 해시 + 코디네이터로 노드가 들어오면 데이터를 균등 재분배. 집계용/원본용 분리 가능(`Kafka→Flink→Cassandra` / `Kafka→Cassandra`).
- **단점**:
  - 행 기반이라 **압축률 낮고 디스크 많이 먹음**.
  - **툼스톤 문제**: 삭제가 "삭제 표식 추가" 방식 → 대량 삭제 시 다 읽어서 터짐.
  - **쿼리 드리븐 모델링**이 걸린다 = 어떤 조건으로 읽을지 **먼저 파티션 키를 설계**해 테이블을 만들어야 함. **구축 단계라 기능 변경이 잦은 우리 상황**에선 테이블이 계속 늘고, 그때마다 Flink가 원천 데이터를 풀스캔해 **수동 집계**를 반복해야 한다.
  - 오래된 데이터를 S3로 내리려면 **별도 파이프라인**이 필요(조회 시 AWS Athena로 S3 속 Parquet(열 기반 파일) 조회). Flink는 **체크포인트·세이브포인트·장애복구 로직 + 클러스터 운영**까지 필요.
  - → **한 달 안에, 학생 4명이 MSA를 관리**하는 상황엔 너무 이상적(=과함).

### 1-3. ClickHouse — 왜 골랐나
- **OLAP 지향** — 쿼리 하나로 집계가 용이(우리 서비스에 딱).
- **기능 추가·변경에도 테이블을 새로 안 만들어도 됨**(토이/구축 단계 유리).
- **계층형 스토리지** — 오래된 데이터는 자동으로 S3로. 최근=CH, 과거=S3. 심지어 **S3의 Parquet를 바로 쿼리**(Athena 같은 추가 스택 불필요).
- **Materialized View** — 데이터가 들어올 때마다 집계 데이터를 자동 추가·머지(완료 시점은 보장 안 돼 조회 쿼리에서 마저 합침). INSERT마다 작동해 **거의 실시간**, **Flink를 관리 안 해도 됨**(리소스↓). *(Flink는 백필 시 배치를 따로 짜야 하지만 MV는 쿼리 딸깍)*
- **append-only**라 읽기·쓰기 처리량 큼.
- **단점(감수)**:
  - **단건 조회 느림** / 수정·삭제 어려움 → 모니터링(신호 데이터)이라 상관없음. 단, **바뀌는 규칙 데이터는 PostgreSQL에 저장**.
  - **한 행씩 INSERT 금지** — MergeTree는 배치로 들어온 데이터를 Part 파일로 압축 후 백그라운드 머지. 한 행씩 넣으면 **Too Many Parts** 에러.
  - 카산드라 대비 **고가용성은 확실히 낮음**. 큰 테이블 JOIN 시 **OOM** 가능 → 비정규화로 회피.

> 🔑 **결론** — 약 1달 내 완성을 위해 **복잡한 설계 대신 간단한 설계**를 택했다. HBase 대비 조회 속도, 카산드라 대비 고가용성을 내주는 대신, **적은 리소스로 최대 퍼포먼스**를 얻는다. 지금도 어려운데 더 어렵게 갈 수 없고, 시간·인원이 부족하다.

### 1-4. ClickHouse에서 고가용성 확보
- **ReplicatedMergeTree + ClickHouse Keeper** — 테이블을 복제(마스터리스). HBase가 ZooKeeper 쓰는 것과 비슷하지만 **CH 내장**이라 운영이 다르다.
- 인프라 쪽에서 **복수 AZ** 사용.

## 2. 왜 DLQ를 카프카 토픽이 아니라 S3에?

카프카 안에 DLQ 토픽을 두는 방식도 가능하지만, 다음 이유로 **S3**를 택했다.

- **토픽 TTL(보통 7일) 안에 못 고치면 유실** — 에러 원인 발견 → 수정 → 재처리를 7일 안에 무조건 끝낼 자신이 없다(시간·인원 부족). **안전빵으로 S3**에 넣어 "차차 고치자".
- **특정 에러만 골라 재처리가 안 됨** — DLQ 토픽을 처음부터 끝까지 읽어 특정 에러만 뽑아야 한다. 에러 종류별 토픽을 만들면 **카프카 부담↑**. **S3는 폴더(경로)로 저장**되니 해당 경로로 가서 고치면 된다.
- **되돌릴 때 파티션 수만큼 오프셋을 손으로** 다뤄야 함.
- **조회 편의** — 카프카 토픽을 보려면 컨슈머를 만들거나 CLI로 훑어야 하지만, **ClickHouse면 SQL 딸깍**. 게다가 CH의 **계층형 스토리지**로 S3를 그대로 활용 가능.

## 3. 카프카 테이블 엔진 vs 별도 적재 처리기

ClickHouse엔 **Kafka Table Engine**(CH가 직접 카프카 소비자 역할 + 배치 적재)이 있는데도 **별도 적재 처리기**를 둔 이유.

- **인정할 점**: 카프카 테이블 엔진을 써도 문제없고 오히려 **아키텍처 단계가 줄어** 좋아 보인다(소비자 역할 + 배치 적재까지).
- **단점**:
  - 나중에 CH를 **다른 저장소(카산드라 등)로 못 바꾼다** — 컨슈머가 CH에 묶이기 때문.
  - 파싱 실패는 Kafka 엔진 옵션으로 해결되지만, **적재 실패 처리 방법은 문서에 없음**(불확실).
  - **적재 처리기가 있으면**: 실패 시 재시도 → 실패분은 S3 → 오프셋 커밋으로 처리 가능.
- **결론**: **미래(저장소 교체)를 생각하면 쓰지 말고**, 단순 프로젝트로 끝낼 거면 써도 된다. → 느슨한 결합을 위해 적재 처리기를 둠.

## 4. 탐지 서비스는 왜 카프카가 아니라 파사드 뒤에?

실시간성만 보면 탐지 서비스가 카프카에 바로 붙어야 할 것 같지만, **파사드를 거치는 현 아키텍처**를 택했다.

- 탐지가 **카프카 바로 다음**에 오면:
  - 에러율처럼 **여러 요청 수의 집계**가 필요하면 그걸 관리할 **Flink를 또 만들어야** 한다.
  - **서비스가 죽어 카프카에 메시지가 아예 안 들어오면**, 탐지 입장에선 아무것도 안 오니 **문제가 생겨도 알람을 못 보낸다**(무소식 = 정상으로 오인).
- **파사드를 거치면**: 파사드 쪽에서 **몇 초 이상 데이터가 안 오면 "비상"을 날릴 수 있다**(부재 탐지 가능).

> ⚠️ 원문에서 이 항목은 "솔직히 잘 모르겠다"고 표시된 **열린 결정**이다. 부재 탐지(heartbeat) 관점의 근거로 파사드 경유를 잠정 채택.

## 5. 질의 파사드의 역할

- **집계 위임 조회** — 화면/탐지에서 API를 쏘면 CH에 쿼리를 날려 **CH가 집계하게 시키고** 그 결과를 가져온다.
- **느슨한 결합** — 나중에 수집 대상·저장소·알림 채널을 바꿔도 **호출 코드는 안 바꿔도 된다**(기술 스택을 뺐다 꼈다 가능).
- **보호막** — 장애 대비로 **조회 시간 범위 상한 · LIMIT · 쿼리 타임아웃** 등을 강제한다.

## 정리

| 질문 | 결론 | 한 줄 이유 |
|---|---|---|
| 저장소? | **ClickHouse** | OLAP라 집계가 쿼리 한 방 + 운영 단순, 1달·4명에 맞음 |
| HBase는? | 제외 | 정합성·고가용성 좋지만 컴포넌트 너무 많아 무겁다 |
| Cassandra는? | 제외 | 확장성 최고지만 쿼리 드리븐 모델링 + Flink 인프라 부담 |
| DLQ 저장소? | **S3** | 토픽 TTL·부분 재처리 한계 회피, 경로로 골라 고침 |
| 카프카 테이블 엔진? | 안 씀(적재 처리기) | 저장소 교체 여지 + 적재 실패 제어 |
| 탐지 위치? | **파사드 뒤** | 무소식(서비스 死)도 탐지 가능 |
| 파사드 역할 | 집계 위임·느슨한 결합·보호막 | 상한·LIMIT·타임아웃 강제 |

			- 확장성 : 멀티 리전 Active-Active 구성이 어려움. 카산드라는 설정 딸깍으로 글로벌 서비스도 가능
		- 정리 : 정합성을 챙기고 고가용성 + 집계 유연성 + 운영 단순함 버리면 이 방법이 좋음
	- Cassandra + flick
		- 장
			- 수평 확장성과 고가용성이 가장 뛰어나다.
				- 고가용성 : 마스터리스 아키텍처라 기존 RDB의 레플리카 처럼 마스터가 죽어도 서비스에 장애나 발생하거나 마스터를 다시 선정할 시간도 필요없다
				- 확장성 : 일관된 해시구조 + 서버가 들어와도 코디네이터 기능으로 기존 서버들의 일부 데이터를 넘겨 받기도 한다.(데이터가 들어와도 데이터가 각 서버 별로 최대한 균등하게 들어간다)
			- 집계용과 원본용을 따로 둘 수 있다
				- 집계용: Kafka ➔ Flink (집계) ➔ Cassandra
				- 원본용: Kafka ➔ Cassandra
		- 단
			- 행 기반이라 압축률이 낮고 디스크를 매우 많이 먹음
			- 툼스톤 문제 : 카산드라의 삭제 방식은 삭제 표식을 추가하는 방식. 대량의 데이터 삭제할 때 다 읽게 될 테니까 컴터가 터짐
			- 쿼리 드리븐한 모델링이 걸린다 + 다양한 조건으로 집계하고 통계내는 것이 힘들다
				- 어떤 조건으로 데이터를 읽은 것인가를 먼저 설계하고 사용을 해야한다
					- 즉, 미리 파티션 키를 지정해서 그 키에 해당하는 테이블을 만든다는 뜻(Cassandra 클러스터 구축 및 파티션 키 설계가 필요)
						- 근데, 우리는 서비스 구축단계라 기능의 변경이 많을 수 있다
							- 그러면 계속해서 추가되는 테이블이 많아진다는 뜻
							- 그 때 마다 flick가 원천 데이터를 풀스캔 해서 집계를 할텐데 그 때 마다 수동으로 진행해야한다(반복 작업이 많아질 듯). 과거 데이터가 없으면 특정 기능은 과거 데이터가 없는 상태로 집계(과거 데이터는 물론 S3에 저장하면됨)
							- 그래서 어느 정도 운영적으로 안정된 서비스가 되면 사용하는 것이 어떤가… → 그래서 질의 파서드를 둠으로써 느슨한 결합을 해서 미래에 기술 스택이 바뀌었을 때 바로 뺏다 꼈다 할 수 있도록 함
				- 오래된 데이터를 S3와 같은 저장소에 넣으려면 별도 데이터 파이프라인 구축이 필요(시간이 오래 걸리는 요소가 될 수 있다). S3에서 데이터 뽑아낼 때 AWS 아테네(S3속 파케이 파일을 조회해주는 기능)를 사용. 파케이 파일 : 열 기반으로 저장하는 파일(CSV의 열기반 버전)
				- flink사용 시 체크포인트·세이브포인트·장애 복구 로직도 필요
				- flink 스트리밍 처리 로직 + 클러스터 인프라 구축 및 유지보수 필요 → 거진 1달안에 만들어야 하는데 할게 너무 많아 → 심지어 MSA를 학생 4명이서 관리하는데 10명도 아니고 너무 이상적인 방식
	- ClickHouse
		- 장
			- OLAP 지향 DB : 쿼리하나로 집계가 용이(우리 서비스)
			- 기능 추가 및 변경이 일어나도 테이블을 따로 만들 필요 없다(토이 프로젝트에서 유리)
			- 데이터가 많이 쌓이면 계층형 스토리지 기능을 통해 데이터 관리가 쉽다
				- 데이터가 쌓이면 오래 된 데이터는 자동으로 S3에 저장되어서 나중에 집계할 때 최근데이터는 CH, 오래된 건 S3에 넣어서 확인 가능
				- 심지어 S3에 있는 파케이 파일을 바로 쿼리 쏴서 조회 가능(AWS 아테나 같이 추가 스택 필요없다)
			- ClickHouse Materialized View 기능
				- 데이터가 들어올때마다 집계데이터를 자동으로 추가하고 기존 집계데이터에 머지도 해줌(대신 완료 시점이 보장이 되지가 않아서 조회 쿼리에서 마저 합쳐야함)
					- flick는 백필할 때 배치를 따로 짜서 원본을 만들어야하는데 MV는 쿼리 딸깍
					- INSERT 할 때마다 작동해서 거의 Real-time이다
					- → Flick 관리 안해도 된다(리소스 줄어든다)
			- 데이터 들어올 때마다 카산드라처럼 append -Only 방식이라 읽기 쓰기 처리량 크다
			- 중요!
				- 우리 서비스 핵심기능 : 알람, 시스템 메트릭, 히트맵, 드래그 선택 모두 집계 데이터 필요
		- 단
			- 단건 조회는 느리다
			- 카산드라처럼 수정 삭제는 힘들다(모니터링이라 상관 없다)
				- 신호데이터는 상관없다
				- 규칙 데이터 설정은 바뀌니까 PG에 저장
			- 한 행씩 넣으면 안됨
				- Merge Tree 방식이라 데이터가 배치로 들어오면 그걸 압축하고(Part 파일) 백그라운드에서 Part끼리 합치는데 한 행 씩 넣으면 애러 난다(Too Many parts)
			- 카산드라 대비 고가용성은 확실히 떨어진다
			- 큰 테이블끼리의 JOIN 시 OOM 가능성 존재→ 비정규화 하면 된다
		- 즉, 우리는 약 1달 이내에 완성할 수 있을 수 있게 복잡한 설계 대신 간단한 설계를 선택. 대신 HBase 대비 조회 속도는 떨어지고, 카산드라 대비 고가용성을 내주는 선택을 함. 지금도 어려운데 여기서 더 어렵게? 그리고 시간과 인원이 부족함 최대한 적은 리소스로 최대의 퍼포먼스가 필요
		- 고가용성 얻는 방법
