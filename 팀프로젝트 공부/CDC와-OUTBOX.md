## 문제
- Dual Write
  - DB에 데이터 저장하고 메시지 큐엔 이벤트를 발행하는 작업을 동시에 수행하는 것
    - 여기서 "동시에"는 하나로 묶인다는 뜻이 아니라, 원자적으로 묶이지 않은 채 두 시스템에 **따로따로** 쓴다는 뜻
    - CASE
      - DB 저장 성공 + 메시지 큐 전송 실패
      - DB 저장 실패 + 메시지 큐 전송 성공
  - 위 문제는 하나의 트랜잭션으로 묶기가 어렵다 → 원자성 보장이 어려움
    - 정합성 : CASE 처럼 실패 가능성이 생기고
      - `@Transactional` 안에서 발행해도 소용없음 : Kafka 발행 성공 후 DB 커밋이 실패하면 Kafka에는 존재하지 않는 주문의 이벤트(유령 이벤트)가 남는다
      - 두 시스템을 하나로 묶는 분산 트랜잭션(2PC/XA)은 Kafka가 지원하지 않는다
    - 가용성 : 트랜잭션 안에서 브로커의 응답을 기다리면 그동안 스레드랑 DB 커넥션을 점유하게 되니까 → 다른 API 까지 말썽

## 해결책

### CDC
- DB 변화를 감지해서 원하는 곳으로 데이터를 흘려보내는 기술
- Pull 방식의 한계 극복
  - 변경 사항 늦게 발견하거나 잦은 조회로 인한 DB 부하 문제
- 중간 상태 누락 방지
  - 현재 값이 아니라 변경된 사실이 필요하다
    - 예 : 5초마다 조회할 때 실제 DB는 대기(0초) → 승인(1초) → 취소(3초)인데, 폴링은 0초의 "대기"와 5초의 "취소"만 봐서 중간의 "승인"을 놓친다
- 위 문제를 해결하기 위해서 앱은 모른 채로 이벤트가 나갈 수 있도록<br>DB가 남기는 변경 로그(binlog / WAL)를 직접 읽는 방식

### Debezium
<details>
<summary>Kafka Connect 위에서 도는 커넥터<br>커넥터 : 데이터베이스나 외부 시스템과 <b>메시지 브로커사이를 연결해 주는 데이터 파이프<br>즉, 컨슈머 및 프로듀서 역할을 코드 없이 대신 해주는 착한 친구</b></summary>

- Source Connector(프로듀서 역할)
  - 외부 시스템에서 데이터를 읽어와서 Kafka 토픽으로 넣어주는 커넥터
  - Kafka Connect에서 Debezium은 이 Source Connector에 해당 (DB → Kafka까지 담당)
- Sink Connector(컨슈머 역할)
  - Kafka 토픽에 쌓인 메시지를 읽어서 다른 목적지 시스템에 저장하는 커넥터
  - Kafka → Elasticsearch·Redis 등으로 옮기는 건 Debezium이 아니라 별도의 Sink Connector가 담당

</details>

- DB의 로그를 읽고 어디까지 읽었는지 그 위치를 추적/기억하는 역할
- Kafka Connect에 특정 테이블을 감시하라는 JSON 파일만 전송하면 알아서 변경사항을 긁어온다 → 코드 수정 없이 가능
- 커넥터가 DB 로그를 읽고 Kafka로 이벤트를 보낼 때
  - CRUD 중 어떤 것이 일어났는 지
    - 실제로는 `op` 필드 : `c`(생성) / `u`(수정) / `d`(삭제) / `r`(초기 스냅샷으로 읽은 행)
  - `before` / `after` 가 뭔지를 같이 보내줌
    - DELETE는 `after = null`로 온다(tombstone 메시지는 설정에 따라 추가) → 소비자가 삭제 처리를 따로 구현해야 함
- 보내는 방식
  - DB에 변경이 일어나면 DB가 로그파일을 만든다
  - Debezium은 네트워크를 통해 DB에 접속해서 로그를 받아간다<br>만약 Debezium 커넥터가 멈추면 안가져간 로그파일을 쌓아둔다 → 디스크 문제

### 한계점
- 의미 해석의 부담
  - CDC는 단순히 어느 컬럼이 어떻게 바뀌었는지만 보여줌<br>즉, 이벤트를 받는 소비자는 상태가 바뀌는 것은 알 수 있지만 왜인지는 모름<br>(e.g.PENDING에서 CONFIRMED로)
  - ⇒ 그래서 Outbox를 사용해서 의미 해석과 컬럼 결합도를 풀어준다
- 높은 결합도
  - DB의 컬럼 이름 하나만 바꾸어도 구독하는 소비자 전부가 흔들림
- 커넥터가 멈추면 로그파일 보존량이 커지는 디스크 용량문제
- CDC를 처음 붙일 때 테이블 전체를 읽는 초기 스냅샷 작업을 보통 한다
  - 이때 대용량 테이블은 점진적으로 데이터를 읽어들이는 'incremental snapshot’ 사용
- CDC가 켜져 있고 Kafka lag이 낮게 유지되어도 최종 데이터가 빨리 반영되었다고 확신할 수 없다
  - 그래서 DB의 변경 시각부터 최종 저장 시각까지 전체 지연을 측정 필수

### 로그파일
- DB가 데이터의 변경 사항을 순차적으로 기록해 두는 로그 파일
  - 종류
    - MySQL
      - binlog (Binary Log)
      - Replication 할 때 사용 + 특정 시점 복구
      - 갑자기 꺼졌을 때 복구는  InnoDB의 redo log가 맡음
        - redo log : DB데이터 저장 전 변경 사항을 적어두는 장소(나중에 배치처리로 DB 데이터 최신화)
    - PostgreSQL
      - WAL (Write-Ahead Log)
      - DB서버가 갑자기 꺼졌을 때 복구 + Replication 할 때 사용

### OUTBOX : 로컬 트렌젝션 활용
- 원자성 보장
  - 한 트렌젝션안에 보내야할 데이터+DB의 OUTBOX테이블에 저장
- 가용성 확보
  - 보내야 할 이벤트가 DB에 안전하게 있어서 Kafka 브로커에 장애가 생겨도 복구 되면 다시 보내면 된다
- 스키마 분리
  - DB 테이블 스키마와 이벤트 스키마를 분리하니까 DB 컬럼이 변경되도 발행되는 이벤트의 구조는 그대로 유지 가능

### Message Relay
- DB에 저장된 아웃박스 메시지를 Kafka로 전달하는 프로그램
- 전달방식
  - Polling
  - CDC
- 문제
  - 릴레이가 이벤트를 Kafka에 보냈는데 기록 전에 죽으면 중복 발송(at-least-once)
  - 그걸 멱등성으로 해결
    - 릴레이는 중복 발송을 막을 수 없어서 **소비자**가 막는다 : "두 번 도착"은 정상, "두 번 처리"가 문제
    - 소비자의 **한 트랜잭션** 안에서 ① `processed_events` 테이블에 `event_id` INSERT(UNIQUE 제약) ② 새 ID일 때만 업무 DB 갱신(재고 차감) → 이미 있는 ID면 건너뜀
    - SELECT로 "처리했나?" 확인만 하면 동시에 들어온 같은 이벤트를 못 막는다 → DB 제약(UNIQUE)이 핵심
    - DB 커밋이 성공한 뒤에 Kafka 오프셋 커밋
  - 추가적으로 이벤트 처리 순서 보장(파티션 키 할당)<br>outbox 테이블관리 전략(스케쥴러기반 배치 삭제, 날짜기반 테이블 파티셔닝)이 필수다
    - 파티션 키 = `aggregate_id`(예 : 주문 ID) → 같은 주문의 이벤트는 같은 파티션에 들어가 순서 유지
    - 단, 순서는 ① 발행 순서 ② 같은 파티션 키 ③ 소비자 처리 순서, 셋이 모두 맞아야 보장된다

## 📎 부록 — 정리하며 빠졌던 것

### A. outbox 테이블에 꼭 있어야 하는 칸

| 칸 | 역할 |
|---|---|
| `event_id` | 멱등 키 — 소비자가 중복 처리를 막는 기준 |
| `aggregate_id` | Kafka 파티션 키 → 같은 대상(주문)의 이벤트 순서 보장 |
| `event_type`와 `payload` | 우리가 설계한 이벤트 내용 — DB 테이블 구조와 분리 |
| `published` / `created_at` | 폴링 릴레이일 때 발행 여부·생성 시각 (선택) |

### B. 릴레이 방식 비교 — 폴링 vs CDC

| 구분 | outbox 폴링 (Polling Publisher) | CDC 릴레이 (Log Tailing) |
|---|---|---|
| **새 메시지를 어떻게 알아?** | outbox에 미발행 행이 있는지 반복 조회 | outbox에 행이 추가된 기록을 DB 로그(binlog/WAL)에서 읽음 |
| **구현** | 스케줄러·별도 워커가 조회 후 발행 | Debezium이 로그를 읽고 발행 |
| **따질 것** | 반복 조회 부하, 조회 간격만큼 지연 | 로그 접근 설정, 커넥터 운영·장애 복구 |

- 둘 다 "outbox에 저장된 메시지를 브로커로 옮기는 방법" — 진화 단계가 아니라 여건에 따른 선택

> ⚠️ **본문의 "Pull 방식의 한계(중간 상태 누락)"와 모순이 아니다.** 누락은 현재 상태를 덮어쓰는 **업무 테이블**을 폴링할 때 생긴다. outbox는 이벤트마다 행이 따로 남아서 늦게 조회해도 전부 가져간다.

### C. 릴레이가 "보내기 전에" 죽으면?
- ① orders 행 + outbox 행 함께 커밋 → ② Kafka로 보내기 전에 앱 종료 → ③ DB에는 주문·이벤트가 그대로 남아 있음 → ④ 재시작 후 미발행 행부터 이어서 전송
- 즉 누락은 없고, 본문의 "보낸 뒤 기록 전에 죽음"(중복)만 신경 쓰면 된다

### D. 외부 API(알림·결제)는 멱등 처리가 다르다
- 외부 호출은 내 DB 트랜잭션에 묶을 수 없다
- 기록 먼저 → 발송 전에 죽으면 **누락** / 발송 먼저 → 기록 전에 죽으면 **중복**
- 그래서 API가 멱등 키를 지원하면 event_id를 넘기고, 아니면 결과 조회로 이미 처리됐는지 확인한다
- Kafka의 exactly-once는 외부 DB 갱신·알림 발송까지 확장되지 않는다

### E. 언제 무엇을 — 업무 테이블 CDC vs Outbox

| 구분 | 업무 테이블 직접 CDC (우체부) | Outbox (우체통) |
|---|---|---|
| **내보내는 것** | 행의 변경 (before / after) | 앱이 의도한 이벤트 (OrderPlaced) |
| **결합** | 테이블 구조에 결합 | 이벤트 계약에 결합 — 테이블이 바뀌어도 OK |
| **앱 코드** | 변경 거의 없음 | outbox 저장 한 줄 추가 |
| **잘 맞는 곳** | 레거시, 검색·캐시·분석 동기화 | 서비스 간 도메인 이벤트, Saga |

- 둘 중 하나를 고르는 게 아니라 함께 쓴다 : outbox 테이블을 CDC로 읽으면 앱이 설계한 이벤트를 로그 기반으로 전달 = **Outbox + Debezium**
- 흔한 순서 : Outbox + 폴링(인프라 추가 없이 시작) → 폴링 지연이 문제가 되고 CDC 운영 여건이 되면 Outbox + Debezium으로 릴레이만 교체

### F. Event Sourcing
- **정의** : "지금 상태"가 아니라 "일어난 일(이벤트)"을 원본으로 저장하고, 상태는 이벤트를 순서대로 반영(fold)해서 만든다
- **왜** : UPDATE는 이전 값을 덮어써서 과거·의도·특정 시점의 상태가 사라진다 (둘 다 CANCELED인데 어느 게 결제 실패로 인한 취소인지 모름)
- **예시 (재고, 이전 상태 + 다음 사건 = 다음 상태)**

| 이벤트 | 판매 가능 수량 |
|---|---|
| E1 입고 +50 | 50 |
| E2 예약 -10 | 40 |
| E3 예약 해제 +3 | 43 |
| E4 예약 -6 | 37 |

- **Snapshot** : 이벤트가 1,000개면 매번 처음부터 계산하지 않고 "1000번까지 반영한 상태"를 저장해 두고 그 뒤 이벤트만 반영한다. 스냅샷은 지워도 다시 만들 수 있지만, 이벤트는 지우면 안 된다
- **Outbox와의 차이** (둘 다 이벤트를 저장하지만 목적이 다르다)

| 구분 | 현재 상태 + Outbox | Event Sourcing |
|---|---|---|
| **원본** | 업무 상태 데이터 (orders 행) | 도메인 이벤트 (사건 기록) |
| **이벤트를 저장하는 목적** | 다른 시스템에 전달하려고 | 상태를 만들고 다시 만들려고 |
| **삭제 기준** | 전달 완료·보존 정책에 따라 정리 | 원본이라 보존·아카이빙 |

- **비용** : 조회가 복잡함(보통 CQRS 읽기 모델을 함께 둠) · 오래된 이벤트와의 호환(이벤트 버전 관리, upcasting) · 도메인을 "사건"으로 모델링하는 팀 역량
- **판단 기준** : "이력이 필요하다" ≠ "ES를 쓴다". 이력·감사만 필요하면 상태 테이블 + 이력 테이블로 충분하다. **이벤트로 상태를 재구성해야 할 때**(원장·정산·포인트·예약), 그것도 필요한 도메인 한 곳에만 쓴다
