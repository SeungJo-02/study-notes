# 이미지 lazy loading과 code splitting

> 🏷️ **프로젝트**: Shelfeed · **작성일**: 2026-08-17

### 이미지 lazy loading
- 웹 페이지에 접속했을 때 삽입된 모든 이미지를 한 번에 다운로드하지 않고, **사용자가 스크롤을 내려 해당 이미지가 화면에 노출될 때쯤 이미지를 로드하는 기술**
- 작동방식
  - 초기 로딩 시 화면 밖에 위치한 이미지는 화면에 회색 박스나 썸네일 형태로 둠<br>이후 이후 사용자가 스크롤을 내려 이미지가 화면 영역에 진입할 때(또는 진입하기 직전에) 실제 이미지 데이터를 서버에 요청하여 화면에 띄움
- 장점
  - 초기 로딩 속도 향상
    - 처음에 다운로드해야 할 전체 리소스의 용량이 크게 줄어들어 첫 화면이 뜨는 속도가 매우 빨라짐
  - 네트워크 및 서버 리소스 절약
    - 용자가 스크롤을 끝까지 내리지 않고 페이지를 이탈할 경우, 보지도 않을 이미지를 다운로드하는 데 낭비되는 네트워크 대역폭과 비용을 아낄 수 있다
- 단점
  - Cumulative Layout Shift, CLS 발생
    - 이미지 로드 전 브라우저가 이미지의 크기를 미리 모르고 있으면<br>화면이 밀리는 현상 발생 <br>→ UX를 해치고 Core Web Vitals 점수를 깎아먹는 주된 원인이 됨
    - 해결책
      - `<img>` 태그에 `width`와 `height` 속성을 명시 
      - CSS로 미리 이미지 영역의 비율(Aspect Ratio)을 잡아두어 공간을 확보
  - 빠른 스크롤 시 빈 화면 노출
    - 이미지 로드 속도가 스크롤을 못따라가면 빈화면만 보일 수 있다
    - 해결책
      - 화면에 완전 진입이 아닌 진입하기 전에 미리 로딩을 시작하도록 구현
  - SEO 악영향 가능성
    - 일부 검색 엔진 크롤러가 스크롤 이벤트를 발생시키지 못해 페이지 하단의 이미지들을 색인(Index)하지 못할 수 있다
    - 해결책
      - 브라우저 네이티브 속성인 `loading="lazy"`나, `noscript` 태그를 활용해 크롤러를 위한 대체 경로를 제공
### code splitting
- 방대한 JS 코드를 하나의 파일(번들)로 묶어서 한 방에 불러오는 대신<br>여러 개의 작은 파일(청크)로 쪼개서 필요한 시점에 필요한 코드만 불러오는 기술
- 작동방식
  - 보통 페이지 단위나 기능/컴포넌트 단위로 코드를 나눈다
    - '메인 페이지'에 접속했을 때는 메인 화면을 구성하는 코드만 먼저 다운로드
    - 이후 사용자가 '결제 페이지' 버튼을 클릭하는 시점에 비로소 결제와 관련된 코드를 서버에서 가져와 실행(Dynamic Import라고 함)
- 장점
  - 초기 상호작용 시간(TTI) 단축
    - 브라우저가 초기에 다운로드나 파싱 실행해야할 JS크기가 줄어들어 <br>페이지가 멈춰 있는 시간이 짧아지고 사용자가 화면을 빠르게 클릭하거나 조작할 수 있게됨
  - 효율적인 캐싱
    - 여러개의 코드로 나뉘어저 있다면 애플리케이션 일부가 업데이트되었을 때<br>변경된 부분의 파일만 새로 다운로드하면 되므로 훨씬 효율적
- 단점
  - 새로운 기능/페이지 이동 시 로딩 지연 
    - 새 기능마다 JS파일을 다운로드해야함 → 지연될 수 있다
  - 해결책
    - 코드를 불러오는 동안 보여줄 로딩 스피너나 스켈레톤 UI 구현 필수
    - 백그라운드에서 미리 가져오는 프리패칭 기술이 있어야 완벽
  - 빌드+설정 복잡도 증가
    - VIte등의 번들러 설정이 복잡해진다
  - 과도한 분할로 인한 네트워크 병목
    - 브라우저가 서버에 요청할 파일이너무 많아저 네트워크 오버해드가 생김
  - 해결책
    - 적절한 크기로 파일이 묶이도록 청크 사이즈 튜닝
