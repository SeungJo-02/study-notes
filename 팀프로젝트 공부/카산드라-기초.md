## 카산드라 요약
- 대용량 쓰기와 읽기 그리고 고가용성을 크게 고려한 분산서비스를 위한 NoSQL이다
- 데이터 정합성은 신경쓰지 않는다

---
## 1장 데이터를 어떻게 담나?
- **keyspace** : DB자체
- **table** : 우리가 아는 테이블
- **row** : 우리가 아는 행
- **column** : 우리가 아는 컬럼
  - 특징 : 컬럼마다 타임스탬프(시간)가 붙는다 → 값이 충돌하면 마지막에 사용된 값이 적용된다
    - **wide-column 방식** : 행마다 다른 컬럼 허용 (e.g. A행은 컬럼 3개, B행은 컬럼 4개)

---
## 2장 PK (매우 중요한 개념)
- 구조 : `PRIMARY KEY ((channel_id, bucket), message_id)`
  - **파티션 키** : 데이터를 어느 서버에 저장?
    - e.g. `(channel_id, bucket)`
  - **클러스터링 키** : 서버 안에서 어떤 순서로 정렬?
    - e.g. `message_id`

---
## 3장 파티셔닝
- **일관된 해싱(Consistent Hashing)** : 카산드라가 파티셔닝 할 때 사용하는 방식
  - **기존 해싱** : 서버 1대 추가하면 거의 모든 데이터를 거의 전부 바꿔야 하니까
    e.g. `서버번호 = 해시값 % 서버개수`
  - **일관된 해싱** : 데이터를 해싱(PK의 파티션 키만을 사용)한 뒤 나온 값으로 해시 링 위에 둔다
    이후 시계방향과 가장 가까운 서버에 저장
    \+ 추가적으로 가상 노드 사용해서 1개의 서버의 위치를 흩뿌려놔서 데이터가 골고루 들어갈 수 있게 한다

---
## 4장 레플리케이션
> 데이터 저장하면 거의 무조건 레플리케이션 사용

- 데이터가 해시링 위에 들어오고 난 뒤 시계 방향으로 그 다음 서버에 복사본을 둠
  - **전략**
    - **SimpleStrategy** : 해시 링에서 원본 데이터를 저장한 첫 서버부터 무조건 시계 방향으로 그 다음 서버들 안에 복사본을 넣는다
      - 만약 그 다음 단계의 복수의 서버가 우연히 같은 건물이나 Rack에 있으면
        정전같은게 발생해서 서버가 꺼지면 원본과 복사본 전체가 모두 날아감
      - 그래서 고통 테스트 용으로 사용
    - **NetworkTopologyStrategy** : 다음 서버들이 같은 데이터 센터나 랙을 사용하고 있다면 그거 까지 고려해서 다음 서버로 분산한다

---
## 5장 일관성 (조절이 가능한)
- 데이터를 몇 개의 레플리케이션에 저장할 지는 사용자가 설정
  - **ONE** : 데이터 저장할 때 복제본 1개만 응답하면 읽/쓰 성공!
    - 빠른데, 데이터 정합성 문제 생길 수 있다
  - **QUORUM** : 설정한 서버에서 절반(n/2+1) 이상 응답하면 읽/쓰 성공!
    - 밸런스 잡힌 방법
  - **ALL** : 복제본 전부 응답하면 읽/쓰 성공!
    - 느린데, 데이터 정합성 가장 정확

---
## 6장 쿼리 라우팅 & Gossip
- **쿼리 라우팅**
  - 마스터/슬레이브가 없음(그래서 해싱사용) → 클라가 아무 서버에나 쿼릴 날려도 됨
    - **코디네이터** : 클라의 요청을 처음 받은 노드
      임시로 대리업무 역할을 한다
    - **대리업무** : 파티션 키 해싱해서 데이터가 어디 서버에 있는 지 확인
      이후 그 서버들에게 데이터를 읽거나 쓰라는 지시하고 그 결과를 클라에게 준다
- **Gossip** : 서로(노드) 죽었는 지 살았는 지 확인
  - 각 노드들이 무작위로 초당 한 번 다른 노드의 상태를 확인
    입소문 마냥 퍼지기 때문에 속도 문제는 없다
  - **Seed 노드** : 추가되는 노드가 가십에 참가하기 위해 찾아가는 고정 노드
    (보통 가장 오래된 노드를 말함)
  - 각 노드들은 아래 숫자들을 들고 댕기면서 데이터 충돌을 막는다
    - **Generation** : 노드가 켜진 시간
      - 죽었다가 재부팅되면 시간이 새롭게 갱신
    - **Version** : 부팅하고 나서 노드의 상태가 바뀔 때마다 버전(숫자)를 하나 올린다

## 7장 저장 엔진 (LSM Tree)
- 클라의 쓰기 → **Commit Log**(디스크에 그냥 순서대로 이어 적기(장애 대비용))
  → **Memtable**(메모리에 정렬된 상태로 보관) → 메모리가 가득차면
  → **SSTable**(디스크 파일, 한 번 쓰면 절대 수정 안 함 = 불변)
- **읽기 흐름**
  - Memtable 속 최신 데이터 확인
  - 없으면 Bloom Filter로 SSTable에 있는 지 확인(없는 건 확실히 없으니깐)
  - 후보 SSTable을 최신 것부터 뒤짐
    - 카산드라는 데이터를 덮어쓰지 않고 계속 새로운 파일을 만들어내기에
      가장 최근에 만들어진 최신 파일부터 역순으로 탐색
- **뒷정리 작업**
  - **Compaction** : 흩어진 SSTable들을 합치고 삭제 표시가 붙은 데이터는 실제로 삭제
    - Cassandra는 삭제할 때 tombstone(삭제표시)만 남긴다
  - **SSTable Indexing** : 키를 통해 바로 데이터가 어디있는지 빠르게 찾게 해주는 인덱싱

---
## 8장 장애 대응
- **Phi Accrual Failure Detector** : 서버가 죽었을 확률이 얼마나 되나를 점수로 계산
  임계점을 넘으면 convicted를 사용해서 라우팅 대상에서 뺀다
  (해시링에선 완전히 지우진 않는다)
- **Hinted Handoff** : 복제본 노드가 잠깐 죽으면 접수 창구가 그 죽은 노드에게 나중에 줄 힌트를 보관
  그 노드가 살아나면 힌트를 줘서 데이터가 유실 되지 않도록 함

---
## 9장 쿼리 중심 모델링
- 어떤 쿼리를 쓸 건가를 먼저 정의 → 쿼리에 맞게 데이터를 비정규화해서 테이블을 만든다
  - 즉, 같은 데이터를 여러 테이블에 중복 저장하는 것이 정상
- **설계 순서(추천)**
  - 파티션 키 정하기 (e.g. `user_id`를 파티션 키 → 유저 번호에 맞도록)
  - 파티션 크기가 너무 크지는 않는 지(Hot Partition) 확인
  - 클러스터링 키 정하기 (e.g. `created_at`)
  - 접근 패턴별로 테이블을 나눠서 중복 저장 (다른 조건으로 찾고 싶다면 새로운 테이블 복사)
    - e.g. `book_id`를 파티션 키로 가지는 완전 새로운 테이블을 하나 만들기

## 10장 그 외
- **SAI** : 파티션 키가 아닌 컬럼으로도 검색가능하게 해주는 보조 인덱스
  - 비정규화를 줄여줌
- **Materialized View(구체화된 뷰)**
  - **카산드라**
    - 원본 테이블에 데이터 INSERT → 백그라운드에서 자동으로 MV테이블에 복사
    - 실무에서는 안쓴다
      - 원본과 MV로 복사되는 과정이 비동기 → 데이터 불일치
      - 마스터가 없어서 각각의 노드들이 알아서 데이터를 맞춰야 해서 성능 개판
  - **일반 DB**

    ![일반 뷰와 구체화된 뷰 비교](images/카산드라-materialized-view.png)

    - 보통 실시간 성은 떨어지지만 계산이 무거운 상황에서 사용(갱신 일이 중요)
      **MySQL** : 자체 구현 해야함
      **PostgreSQL** : MView가 네이티브 기능임
- **검색 인덱싱** : 전문 검색은 Elasticsearch 연동

## 11장 면접에선 뭐라 말하냐?
- 일관성보다 가용성이 중요해서 우리 서비스에 사용했다
- 쓰기가 압도적으로 많을 때 (LSM 트리 덕분)
- 저렴한 서버를 가로로 계속 늘려 확장해야할 때
- **[피하기]**
  - 강한 일관성이 꼭 필요할 때 (e.g. 은행)
  - JOIN, 복잡한 다중 테이블 쿼리가 필요할 때
  - 즉석에서 아무 조건으로나 집계·조회해야 할 때
  - 트랜잭션/ACID가 필요할 때

## 카산드라 특징 [간단]
- **CQL** : 카산드라 쿼리 언어 사용
  - 사용 가능 : `SELECT`, `INSERT`, `UPDATE`, `DELETE`
  - 사용 불가 : JOIN, 서브쿼리, FK
- **Masterless 분산 아키텍처**
  - **Peer-to-Peer 구조** : 모든 노드(서버)가 동등한 역할을 한다
    - 마스터(쓰기), 슬레이브(읽기)처럼 나뉘지 않는다
    - 메인 서버가 없어서 SPOF가 없다
  - **무중단 수평확장** : 트래픽이나 데이터 증가 시 서버 안내리고 클러스터에서 새 노드를 추가하기만 하면 데이터가 자동 분산 → 성능이 좋아짐
- **Query-Driven 데이터 모델링**
  - 어떤 쿼리를 쓸 건가를 먼저 정의 → 쿼리에 맞게 데이터를 비정규화해서 테이블을 만든다
  - 데이터가 분산되어 저장되어 있어서 Key를 통해 검색해야하는 제약
- 즉, 대규모 데이터를 쓰고 읽는데에는 매우 훌륭
  통계나 분석 집계 이런 곳에는 사용하기가….
