# 파티셔닝과 샤딩

> 📝 **Notion**: https://app.notion.com/p/3cfd7d6851ff800980ecdcba6d5e212b
> 🏷️ **프로젝트**: MoniMonitor · **작성일**: 2026-09-02

> **🧩 한 줄 요약** — 데이터가 한 DB로 감당 안 될 때 쪼갠다. **파티셔닝** = 한 DB 인스턴스 안에서 테이블을 물리 조각으로 나누기(Scale-Up), **샤딩** = 그 조각을 여러 DB 서버로 흩뿌리기(Scale-Out). 샤딩은 조인·트랜잭션을 잃으므로 **최후의 수단**.

---

## 1. 언제 쓰나 — 단일 DB의 한계

단일 테이블·단일 DB 구조가 다음 벽에 부딪혔을 때 분할을 검토한다.

- **I/O 병목** — 데이터가 많아지면 인덱스 깊이가 깊어지고 디스크 접근 비용이 커진다.
- **동시성 충돌** — 트랜잭션 경합·락 대기 시간 증가.
- **운영 비용 폭증** — 백업·복구·배포 시간이 데이터 크기에 비례해 커진다.
- **물리적 한계** — CPU·메모리·디스크를 더는 못 키우는 지점.

> **🪜 순서가 중요하다** — 인덱스 튜닝 → 읽기 복제(Read Replica) → 파티셔닝 → **샤딩** 순으로 올라간다. 샤딩부터 지르면 얻는 것보다 잃는 게 많다.

---

## 2. 파티셔닝 (Partitioning)

**하나의 논리 테이블**을, **같은 DB 인스턴스 안에서** 여러 물리 조각으로 쪼갠 것. 애플리케이션은 여전히 테이블 하나만 보고, 쪼개고 합치는 건 DB 엔진이 알아서 한다.

### 2-1. 나누는 방향 — 수평 vs 수직

| 방향 | 기준 | 예시 |
| --- | --- | --- |
| **수평(Horizontal)** | **행(row)** 으로 분리 | 2024년 주문 / 2025년 주문 |
| **수직(Vertical)** | **열(column)** 으로 분리 | 자주 읽는 컬럼 vs 큰 BLOB·설명 컬럼 분리 |

### 2-2. 수평 파티셔닝 종류

| 종류 | 기준 | 예시 |
| --- | --- | --- |
| **Range** | 날짜·숫자 범위 | 월별 로그, 연도별 데이터 |
| **List** | 특정 값 목록 | 지역코드(서울·부산) |
| **Hash** | 해시 함수로 균등 분산 | 특정 값 쏠림(데이터 스큐) 방지 |
| **Composite** | 둘 이상 조합 | List + Hash |

### 2-3. 파티션 키와 프루닝 — 핵심 함정

파티션을 나눈 기준 컬럼이 **파티션 키(Partition Key)**. 쿼리의 `WHERE` 에 이 키가 있어야 DB가 관련 없는 파티션을 통째로 건너뛴다 — 이게 **파티션 프루닝(Partition Pruning)** 이고, 파티셔닝이 빨라지는 유일한 이유다.

> **⚠️ 파티션 키 없이 조회하면 오히려 느리다.** 프루닝이 안 되면 모든 파티션을 다 뒤지는데(전체 스캔), 쪼개진 만큼 조각마다 스캔이 붙어 안 나눈 것보다 손해다. → 파티션 키는 **가장 자주 쓰는 조회 조건**으로 잡아야 한다.

---

## 3. 샤딩 (Sharding)

**수평 파티셔닝을 여러 대의 서로 다른 DB 서버(인스턴스)로 분산**시킨 것. 데이터가 물리적으로 다른 장비에 흩어지고, 어느 서버에 있는지는 **샤드 키(Shard Key)** 로 라우팅한다.

- **조인이 어려워진다** — 다른 서버에 있는 데이터끼리 붙이는 **크로스 샤드 조인**은 DB가 대신 못 해주고 애플리케이션이 모아서 합쳐야 한다.
- **최후의 수단** — 확장성은 얻지만 조인·트랜잭션·운영 편의를 내준다.

> **🕳️ 샤딩이 데려오는 새 문제들**
>
> **핫스팟** — 샤드 키를 잘못 고르면 한 샤드에 트래픽이 쏠린다(스큐). · **크로스 샤드 트랜잭션** — 여러 샤드에 걸친 ACID가 깨져 분산 트랜잭션/Saga가 필요. · **ID 충돌** — 서버마다 auto-increment가 겹치므로 UUID·Snowflake 같은 전역 ID를 써야 함. · **리샤딩** — 샤드를 늘리면 데이터 재배치가 필요하고, 그 고통을 줄이는 게 Consistent Hashing.

---

## 4. 파티셔닝 vs 샤딩

|  | 파티셔닝 | 샤딩 |
| --- | --- | --- |
| **물리적 위치** | 같은 인스턴스 안(단일) | 서로 다른 DB 인스턴스(다수) |
| **확장 방향** | Scale-Up | Scale-Out |
| **관리 주체** | DB 엔진 | 보통 애플리케이션/미들웨어 |
| **SQL 수정** | 불필요(투명) | 필요(라우팅 로직) |

<details>
<summary>🔎 헷갈리기 쉬운 것 — 샤딩 vs 복제(Replication)</summary>

  - **샤딩** = 서로 **다른** 데이터를 여러 서버에 쪼개 담는다(용량·쓰기 분산).
  - **복제** = **같은** 데이터를 여러 서버에 복사한다(읽기 분산·가용성).
  - 둘은 목적이 다르고 보통 **함께** 쓴다 — 각 샤드를 복제로 이중화.

</details>

## 5. 정리

| 개념 | 한 줄 정의 |
| --- | --- |
| 파티셔닝 | 한 DB 안에서 테이블을 물리 조각으로 분할 (DB 엔진이 처리) |
| 수평/수직 | 행으로 자르기 / 열로 자르기 |
| 파티션 프루닝 | 파티션 키로 조회 시 무관한 조각을 건너뛰는 것 = 빨라지는 이유 |
| 샤딩 | 수평 파티션을 여러 DB 서버로 분산 (앱이 샤드 키로 라우팅) |
| 샤드 키 | 데이터가 어느 서버에 갈지 결정하는 기준 컬럼 |

3. Range 파티션 테이블을 파티션 키 없이 조회하면 왜 더 느려질 수 있나?

<details>
<summary>답</summary>

  1. 둘 다 데이터를 쪼개지만 파티셔닝은 **같은 DB 인스턴스 안**, 샤딩은 **여러 DB 서버**로 나눈다.
  2. 확장성은 얻지만 **조인·트랜잭션·전역 ID·운영 편의**를 잃어, 인덱스·복제·파티셔닝으로 안 될 때만 감수하는 트레이드오프이기 때문.
  3. **파티션 프루닝**이 안 돼 모든 파티션을 전부 스캔하는데, 조각이 나뉜 만큼 스캔이 중복돼 안 나눈 것보다 손해다.

</details>

<details>
<summary>📄 원본 노트 (정리 전 원문 보관)</summary>

  - 단일 테이블, 단일 DB 구조가 한계에 도달했을 때 사용
    - I/O 병목 심화 : 데이터의 많아짐 → 인덱스 깊이 증가, 디스크 비용 상승
    - 동시성 충돌 증가 : 트랜잭션 경합, 락 대기시간 증가
    - 운영 비용 폭증 : 백업,복구,배포 시간의 기하급수적 증가
    - 물리적 한계 도달 : CPU 메모리 디스크 확장의 필요
  - 파티셔닝
    - 하나의 서버안에서 DB테이블을 분리한 것(물리적으로)
      - 수평 파티셔닝
        - 행을 기준으로 테이블을 분리
      - 수직 파티셔닝
        - 열을 기준으로 테이블을 분리
      - 종류
        - Range - 날짜 숫자 등 기준으로 분할(e.g. 월별로그, 연도 데이터)
        - List - 특정 값의 목록을 기준으로 분할(e.g. 지역코드-서울, 부산)
        - Hash - 해시 함수로 데이터를 균등하게 분산(특정 값 쏠림 방지 전략)
        - Composite - 두 개 이상의 파티션 사용(e.g. List + Hash)
    - 해당 파티션으로 나눈걸 기준으로 쿼리쳤을 때만 성능이 나오고 풀스캔이면 오히려 느려지는 단점
  - 샤딩
    - 수평 파티셔닝을 여러 대 서버로 분산 시킨것
      - 데이터가 물리적으로 분리
      - 샤딩을 하면 join 연산이 힘들어짐
      - 최후의 수단이다

  |  | 파티셔닝 | 샤딩 |
  | --- | --- | --- |
  | 물리적 서버(분산) | 같은 인스턴스안(단일) | 서로 다른 DB 인스턴스(다수) |
  | 확장(성) 방향 | Scale-Up | Scale-Out |
  | 관리(책임)주체 | DB엔진 | 보통 애플리케이션/미들웨어 |
  | SQL 수정 | 불필요 | 필요 |

</details>
