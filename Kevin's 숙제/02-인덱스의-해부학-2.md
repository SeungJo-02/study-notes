## 7. 인덱스가 안 타는 이유

- 함수적용
	- e.g. `WHERE YEAR(created_at) = 2026`
		- 인덱스 컬럼에 함수 적용하면 각 데이터의 year를 알기위해 풀스캔을 하게 된다
		- 즉, 인덱스가 걸린 컬럼 자체에 함수를 씌우면 풀스캔(No 인덱스)
	- 해결책
		- 인덱스가 걸림 컬럼은 함수로 건들지 않고 조건을 사용하기
			- e.g. `WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'`
		- 함수 기반 인덱스 사용 - 미리 결과를 B-Tree에 저장
			- e.g. `CREATE INDEX idx_lower_email ON users ((LOWER(email)));`
		- JSON 데이터 안에서 특정 값만 인덱싱
			- `ALTER TABLE users ADD KEY idx_city ((CAST(user_info->>'$.city' AS CHAR(30))));`
				- `CAST : CHAR(30)으로 고정해서 넣어라 `
				- `user_info->>'$.city : JSON에서 city라는 키 값만 뽑기`
- 묵시형 형변환
	- e.g. `WHERE phone = 01012345678`
		- 컬럼이 VARCHAR 라면 인덱스도 문자열 기준으로 정렬
		- 문자와 숫자를 비교하면 DB는 문자열 컬럼의 모든 값을 숫자로 형변환하여 결정한다<br>즉, 모든 데이터 형변환을 하기에(풀스캔) 인덱스 적용이 안됨
- LIKE 앞 와일드 카드
	- e.g. WHERE name LIKE '%승조'
		- Leftmost Prefix Rule과 같다
			- '김%'은 가능하지만
			- '%승조'는 첫 글자가 뭔지 몰라서 풀스캔 한다
			- '%승조' 같은 검색은 B-Tree 인덱스로는 해결 안됨
	- 해결책
		- GIN이나 Full-Text Search 혹은 ES 도입

## 8. 운영 기술

- Invisible Index (투명 인덱스)
	- e.g. `ALTER TABLE orders ALTER INDEX idx_status INVISIBLE;`
		- 디스크엔 있지만 검색할 때만 DB옵티마이저가 무시한다
	- 인덱스를 지울 때 필요한 인덱스를 지우게 되면 대참사가 난다
		- 인덱스를 물리적으로 삭제하지 않고 DB엔진의 눈에만 안보이게 가리기
			- 가렸는데 문제가 없으면 DROP
			- 문제가 생기면 `VISIBLE`로 즉시 복구
- 인덱스 파편화 (Fragmentation)
	- B-Tree 인덱스의 데이터는 디스크의 페이지(노드)단위로 저장
		- INSERT, DELETE 하다보면 페이지에 공간이 생김(100개 들어갈 수 있는데 4개만 있는 등)
		- 그러다가 여러 바구니에 흩어져서 집어 넣는다면 디스크 조회(I/O)증가→성능 OMG
	- 해결책
		- MySQL
			- `OPTIMIZE TABLE` , `ALTER TABLE ... ENGINE=InnoDB` 사용
				- Online DDL을 지원하여 서비스 중단 없이 가능
		- PostgreSQL
			- `REINDEX` : 기본 청소 명령어
				- 청소하는 동안 락이 걸려 사용자가 데이터 수정이 불가
			- `pg_repack` : 락 없이 인덱스를 다시 만들어 주는 확장 프로그램(지금 표준)

## 9. 인덱스가 쓰기를 느리게 만드는 구조

- 인덱스 없을 때(INSERT)
	- 그냥 데이터 삽입
- 인덱스 있을 때(INSERT)
	- 인덱스 1,2,3 에 각각 넣기
	- 즉, 데이터 1개를 INSERT 할 때 걸려있는 인덱스가 5개라면
		- → 총 5번의 쓰기 작업이 필요
- 결론
	- 읽기가 많은 서비스라면
		- 인덱스 넉넉하게 만들기
	- 쓰기
		- 인덱스 최소화 혹은 0에 수렴하게 안그러면 DB가 뻑난다
