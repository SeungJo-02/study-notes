> 🧩 **한 줄 요약** — 인덱스는 *정렬된 B+Tree*다. 이 구조 하나가 컬럼 순서(정렬)·커버링(테이블 룩업 제거)·범위 스캔(리프 링크드 리스트)을 전부 설명한다.

## 1. B-Tree vs B+Tree

핵심 차이는 **데이터를 어느 노드에 두느냐** 하나다.

| 구분 | B-Tree | B+Tree |
|---|---|---|
| 데이터 위치 | 모든 노드에 키+데이터 | 리프 노드에만 데이터 (상위는 방향키만) |
| 차수 / 높이 | 데이터가 커서 차수 적음 → 높이↑ → I/O↑ | 키만 있어 차수 많음 → 높이↓ → I/O↓ |
| 단건 검색 | 상위 노드에 데이터가 있으면 더 빠를 수도 | 큰 차이 없음 |
| 범위 검색 | 느림 | 리프끼리 연결 → 빠름 |

> 💡 한 노드(층)를 읽는 것 = **1 페이지 읽기 = 1 디스크 I/O**. 그래서 *트리 높이가 곧 성능*이다. 요즘 DB가 말하는 B-tree는 사실상 **B+Tree**다.

### 1-1. B-tree의 구조

- **루트 노드** — 모든 검색의 시작점
- **브랜치 노드** — 데이터가 어느 방향인지 범위 기반 길 안내 (데이터 없음, 자식 주소만)
- **리프 노드** — 실제 데이터가 정렬된 상태로 저장, 리프끼리 링크드 리스트로 연결

## 2. 복합 인덱스와 컬럼 순서

```sql
CREATE INDEX idx_name_age ON users(name, age);
```

> 🚫 **Leftmost Prefix (최좌측 접두사 규칙)** — 왼쪽 컬럼부터 순서대로 매칭해야 인덱스를 탄다. `name` 없이 `age`만 조건에 걸면 정렬 순서를 따라갈 수 없어 **풀스캔**.

컬럼 순서가 중요한 이유 = 인덱스가 **정렬된 구조**이기 때문. `(name, age)`는 "name으로 먼저 정렬, 같은 name 안에서 age로 정렬"된 사전과 같다.

<details>
<summary>⚠️ 실무 함정 — range 조건 뒤의 컬럼은 인덱스를 못 탄다</summary>

- 인덱스 `(a, b, c)` 에서 `WHERE a = 1 AND b > 2 AND c = 3` 를 실행하면
- `a` 는 seek, `b` 는 range 스캔까지 인덱스를 타지만 **`c` 는 못 탄다.**
- `b` 가 범위(`>`)로 열리는 순간 그 뒤 정렬이 흐트러져 `c` 로는 좁힐 수 없다. `c` 는 필터로만 걸린다(EXPLAIN `Using index condition`).
- 그래서 **등호(`=`) 컬럼을 앞에, 범위(`>` `<` `BETWEEN`) 컬럼을 뒤에** 두는 게 복합 인덱스 설계의 기본이다.
</details>

## 3. Clustered vs Non-Clustered

| 구분 | Clustered (군집) | Non-Clustered (Secondary) |
|---|---|---|
| 정체 | 테이블 실데이터 자체가 PK 순서로 정렬 저장 | PK 외 컬럼 검색용으로 따로 만든 인덱스 |
| 리프에 든 것 | Row 전체 | 인덱스 컬럼 + **PK 값** |
| 개수 | 테이블당 1개 (정렬 기준이 1개) | 여러 개 가능 |

- InnoDB는 PK를 만들면 **무조건 PK 순서로** 테이블이 정렬된다 → PK 검색은 데이터 직접 접근, 추가 단계 없음.
- "테이블당 1개"는 컬럼 1개가 아니라 **정렬 기준 1개**라는 뜻. (키順이면서 몸무게順일 수는 없다. 단 복합키로 기준 1개는 만들 수 있음)
- 실무에선 Clustered(뼈대) + Non-Clustered(추가 검색로)를 **거의 항상 같이** 쓴다.

### 3-1. Table Lookup — 세컨더리 인덱스의 약점

세컨더리 인덱스로 조회 시, 인덱스에 없는 컬럼을 원하면 검색이 **2번** 일어난다.

```plain text
1) 세컨더리 인덱스 리프에서  PK 값을 찾는다
2) 그 PK로 Clustered Index를 다시 타고 내려가  Row를 가져온다   ← 이게 Table Lookup
```

→ I/O가 늘어 성능이 떨어진다.

### 3-2. Covering Index — 테이블 룩업을 없앤다

> ⚡ 쿼리에 필요한 **모든 컬럼이 세컨더리 인덱스 안에** 있으면 2단계(Table Lookup)를 완전히 생략한다. 커버링 인덱스가 빠른 이유는 오직 이것 하나다. (EXPLAIN에 `Using index` 표시)

## 4. Index Seek vs Scan

B+Tree를 DB가 실제로 탐색하는 3가지 방식.

| 방식 | 동작 | 예 | EXPLAIN |
|---|---|---|---|
| Index Seek | 루트→브랜치 타고 원하는 리프에 바로 꽂힘 | `WHERE id = 100` | `ref` `eq_ref` (Best) |
| Index Range Scan | Seek로 시작점 찾고 리프 링크 따라 옆으로 스캔 | `WHERE id BETWEEN 1 AND 10000` | `range` |
| Index Full Scan | 첫 리프~마지막 리프 전체 순회 (Root/Branch 안 탐) | — | `all` (Worst) |

> 💡 Full Scan이라도 세컨더리 인덱스는 테이블보다 작아 **테이블 풀스캔보단 낫다.** (Clustered의 Full Scan은 곧 테이블 풀스캔)

## 5. 인덱스의 쓰기 비용

인덱스는 읽기엔 강하지만 **쓰기엔 짐**이다. 모든 DML이 모든 인덱스를 건드린다.

- **INSERT** — 테이블 행 추가 + 모든 인덱스에 키 추가
- **UPDATE** — 변경된 컬럼의 인덱스 갱신
- **DELETE** — 행 삭제 + 모든 인덱스에서 키 제거

> 인덱스 5개면 INSERT 1번에 **쓰기 6번** (테이블 1 + 인덱스 5)

<details>
<summary>OLTP란? — 왜 쓰기 비용이 서비스 성능을 좌우하나</summary>

- **OLTP (Online Transaction Processing)** — 작지만 빈번한 데이터 변경을 빠르고 정확히 처리하는 시스템. RDBMS가 지향하는 스타일.
- 특징: 잦은 INSERT/UPDATE/DELETE · 작은 트랜잭션과 높은 동시성 · 데이터 무결성이 생명.
- 수만 명이 동시에 작은 쓰기를 날리므로, 인덱스 하나가 늘리는 쓰기 비용이 곧 처리량 저하로 직결된다.
</details>

## 6. 인덱스 과다와 관리

### 6-1. 인덱스가 너무 많으면 생기는 3가지 문제

1. **저장공간** — 인덱스가 테이블보다 커지는 배보다 배꼽
2. **쓰기 증폭** — 모든 DML이 모든 인덱스를 갱신
3. **옵티마이저 혼란** — 후보가 많으면 오답 확률↑, 실행계획 불안정

### 6-2. 미사용 인덱스 탐지

**MySQL 8.0 — Invisible Index** (바로 DROP 대신 옵티마이저에게만 숨김)

```sql
ALTER TABLE orders ALTER INDEX idx_old INVISIBLE;
-- 수일 지켜보고 문제 없으면 DROP, 성능 나빠지면 즉시 VISIBLE로 복구
```

**PostgreSQL — 한 번도 안 쓴 인덱스 조회**

```sql
SELECT indexrelname, idx_scan
FROM pg_stat_user_indexes
WHERE idx_scan = 0;
```

## 7. MySQL vs PostgreSQL 인덱스 차이

### 7-1. InnoDB + UUID PK가 위험한 이유

세컨더리 인덱스 리프마다 **PK 값이 복사**되어 들어간다. PK가 36바이트 UUID면:

- 인덱스 5개면 무거운 UUID가 5벌 복사 → 인덱스 덩치가 기형적으로 커짐
- 페이지당 데이터↓ → 트리 높이↑ → 검색 속도↓
- 게다가 UUID는 정렬이 랜덤이라 **페이지 분할(Page Split)**이 잦다

> ✅ 대안: **시간순 UUID** (UUID v7, ULID, TSID) — 앞부분이 생성 시간순으로 정렬되어 페이지 분할과 인덱스 비대화를 막는다.

### 7-2. PostgreSQL만의 무기

- **HOT (Heap-Only Tuple) Update** — 변경 컬럼이 인덱스에 없으면 인덱스 트리를 안 건드리고 데이터만 수정하고 주소 이전 했다고 넘기기 → 쓰기 증폭 방어(인덱스를 안건든다)
- **Partial Index** — 특정 조건을 만족하는 행만 모아 인덱스 생성 (가성비 끝판왕)

```sql
CREATE INDEX idx_active ON orders(user_id) WHERE status = 'ACTIVE';
```

<summary>복합 인덱스 (a, b, c) 에서 WHERE b = 1 AND c = 2 는 인덱스를 타나요?</summary>

안 탄다. **최좌측 접두사 규칙 위반.** `a` 가 조건에 없으면 정렬 순서를 따라갈 수 없다.

<details>
<summary>PK를 UUID로 쓰면 어떤 문제가 있나요?</summary>

정렬 순서가 랜덤이라 **페이지 분할이 잦고**, InnoDB에서는 세컨더리 인덱스 리프에 PK가 들어가므로 **세컨더리 인덱스 크기가 커진다.**
</details>

<details>
<summary>인덱스를 추가했는데 오히려 느려진 경우가 있나요?</summary>

- 카디널리티가 낮아 풀스캔보다 느린 경우 (인덱스 경유 랜덤 I/O > 순차 스캔)
- 인덱스가 너무 많아 쓰기 성능이 떨어진 경우
</details>

## 9. 정리

| 개념 | 한 줄 정의 |
|---|---|
| B+Tree | 리프에만 데이터 + 리프 링크드 리스트. 낮은 높이 + 범위 검색 강함 |
| Leftmost Prefix | 복합 인덱스는 왼쪽부터 순서대로 매칭해야 탄다 |
| Clustered | 테이블 자체가 PK 순 정렬. 테이블당 1개 |
| Covering Index | 필요한 컬럼이 인덱스 안에 다 있어 Table Lookup 생략 |
| 카디널리티 | 컬럼 값의 다양성. 낮으면(성별 등) 인덱스가 무의미 |

세 줄 요약:
- 컬럼 순서가 중요한 이유 → **정렬 순서** 때문
- 커버링 인덱스가 빠른 이유 → **테이블 룩업 제거** 때문
- 카디널리티가 낮으면 무의미한 이유 → **옵티마이저가 풀스캔이 낫다고 판단**하기 때문

> 🧠 슬로우 쿼리의 90%는 인덱스로 해결된다. 하지만 **인덱스 과다의 30%는 인덱스를 줄여서 해결된다.**

<details>
<summary>📄 원본 노트 (정리 전 원문 보관)</summary>

**B-Tree**
- 모든 노드에 데이터가 들어가 있다
	- 즉, 키와 데이터가 같이 들어가 있어 한 노드에 차수가 적게 들어간다<br>한 노드에 들어갈 수 있는 크기가 정해져 있는데 데이터는 크기가 크다
	- 그러면 높이가 커지고 그러면 I/O 가 많아진다

**B+Tree**
- 리프 노트에만 데이터가 들어가 있다
	- 뿌리 및 중간노드는 데이터는 없고 키(방향키)만 존재하고 데이터는 가장 밑 리프노드에만 있다
		- 그러면 한 노드에 차수가 많이 들어갈 수 있어 트리 높이가 작아져 I/O 횟수가 떨어짐→성능up
	- 단건 검색은 B-Tree랑 큰 차이가 없고 운이 좋으면 B-Tree가 더 빠름<br>대신 범위 검색은 B+Tree는 가장 밑 노드끼리 이어져 있기에 더 빠름

**B-tree의 구조**
- 루트 노드
	- 데이터 검색은 무조건 이 루트노드를 통해 시작
- 브랜치 노드
	- 찾고자하는 데이터가 어느 방향에 있는 지 범위를 기반으로 길안내 역할
- 리프 노드
	- 실제 데이터가 정렬된 상태로 저장되어 있는 노드
- 한 층(노드)을 읽는 것 = 1 페이지(Page) 읽기 (디스크 I/O)
- 차수증가
	- B-tree
		- 브랜치노드에 실제 데이터가 저장됨
			- 하나에 노드에 들러갈 수 있는 사이즈가 존재 근데 데이터는 사이즈가 커<br>그래서 차수가 적게 들어가고 그러니까 트리의 깊이가 깊어짐<br>이는 I/O 횟수가 많아지고 그래서 성능이 떨어짐
	- B+tree
		- 브랜치노드에 자식노드의 주소만 저장됨<br>차수 up 트리 깊이 down → I/O 감소, 성능 up
		- 리프노드 끼리 연결되어 있어 순차읽기 가능

**즉 요즘의 B-tree는 B+tree다**

**복합 인덱스와 컬럼 순서**
- e.g. `CREATE INDEX idx_name_age ON users(name, age);`
- **Leftmost Prefix : 왼쪽부터 순서대로 매칭을 안하면 인덱스 안타고 풀스캔 한다**

**Clustered vs Non-Clustered**
- Clustered Index
	- 테이블 실데이터 자체가 PK 순서로 저장된다.(모든 데이터가 리프노드에 다 있음)
	- PK 검색 = **데이터 직접 접근**, 추가 단계 없음.
	- InnoDB는 테이블당 하나만 가능.
	- 클러스터형 인덱스 트리의 리프노드를 열어보면, 그 안에 테이블의 실제 Row 전체가 있다
	- MySQL에서는 PK를 생성하면 무조건 그 PK를 기준으로 테이블 데이터가 정렬
- Non-Clustered(Secondary)Index
	- PK가 아닌 다른 컬럼으로 빠르게 검색하기 위해 추가적으로 만드는 인덱스
	- 인덱싱된 컬럼만 찾는다면
		- Non-Clustered Index 안에서 컷
	- 인덱싱된 컬럼 밖에 컬럼이 있다면
		- 인덱스 리프에 **PK 값**이 들어 있다.
		- 인덱스 검색 → PK 획득 → PK로 다시 검색.
		- 이 두 번째 단계가 **테이블 룩업**이다.
- Table Lookup : 세컨더리 인덱스의 약점
	- 세컨더리 인덱스는 2번의 검색이 들어갑니당
	- 1번 : 리프노드에서 PK 값을 찾아낸다
	- 2번 : 그 PK 값을 가지고 다시 Clustered Index 를 타고 내려가서 데이터를 가져온다
	- 즉, I/O가 많아져서 성능이 좀 떨어진다
- 커버링 인덱스가 빠른 이유가 바로 테이블 룩업을 생략하기 때문이다
	- 세컨더리에 모든 인덱스 컬럼이 있다면 Table Lookup이 필요가 없다
	- 즉, 쿼리에 필요한 모든 데이터가 세컨더리 인덱스 자체에 포함되어 있어, 테이블 룩업을 완벽하게 생략할 수 있는 상태가 커버링 인덱스
- 궁금증
	- Clustered Index에서 "테이블당 1개"라는 게 "컬럼 1개"라는 뜻?
		- 정렬기준이 1개라는 뜻
		- e.g. 키 순서대로 순서이면서 몸무게 순서대로 정렬을 할 수 없는 것처럼
		- 대신 복합키를 사용하면 1개의 기준을 만들 수는 있다
		- 즉, 컬럼은 여러개 가능 정렬기준이 테이블당 1개
	- Clustered Index와 Non-Clustered Index는 한 테이블에서 같이 쓸 수 있나?
		- 그렇다 실무에서 거의 무조건 같이 쓴다
		- 기본뼈대가 Clustered Index : PK 지정 시 데이터가 PK 순서대로 정렬되어 디스크에 저장
		- 추가 검색로 Non-Clustered Index : 다른 컬럼에 인덱스를 복수 개 만들 수 있다

**Index Seek vs Scan**
- B+tree 구조를 DB가 실제 어떻게 탐색하는가 3가지
- Index Seek
	- 루트 노드 → 브랜치 노드를 타고 원하는 리프노드에 꽂히는 것
		- e.g. `WHERE id = 100`
- Index Range Scan(범위 검색)
	- 시작점을 찾고 범위만큼 쭉 읽는 방식
	- 리프 노드 간 연결된 리스트 사용
		- 시작점을 Index Seek로 찾고 리프노드끼리의 선을 따라 종료지점이 나올 때까지 옆으로 스캔해서 읽기
		- 범위가 너무 넓으면 당연히 느려짐
		- e.g. `WHERE id BETWEEN 1 AND 10000`
- Index Full Scan
	- 인덱스 전체를 순서대로 읽는 방식
	- Root, Branch를 안타고 가장 첫 번째 리프 노드부터 가장 마지막 리프 노드까지 처음부터 끝까지 다 훑어보는 것
	- 궁금증
		- 그럼 풀스캔 아님?
			- Clustered Index 는 그런데
			- Non-Clustered Index는 상대적으로 적으니까 풀스캔 보단 낫다
- 참고
	- EXPLAIN 사용하면 아래 3가지가 나오고 그걸보고 판단하면 됨
		- `ref, eq_ref` : Index Seek(Best)
		- `range` : Index Range Scan
		- `all` : 풀스캔 (Worst)

**인덱스의 쓰기 비용**
- 인덱스는 읽기에는 효과적이지만 쓰기에는 잼병이다
	- INSERT : 테이블에 행 추가 + 모든 인덱스에 키 추가
	- UPDATE : 변경된 컬럼의 인덱스 갱신
	- DELETE : 테이블에 행 삭제 + 모든 인덱스에 키 제거
	- e.g.
		- 인덱스가 5개면 INSERT 하나에 6번의 쓰기 발생(테이블에 1개, 인덱스에 5개)
	- OLTP(Online Transaction Processing)란?
		- 실시간 데이터 처리 시스템을 말함(처리 스타일이고 RDBMS가 이런 스타일 지향이다)
		- 수많은 사용자가 동시에 발생시키는 '작지만 빈번한 데이터 변경 작업'을 빠르고 정확하게 처리하는 데 특화된 시스템
		- 특징
			- 빠르고 잦은 데이터 변경 (INSERT / UPDATE / DELETE가 빈번하게 일어남)
			- 작은 단위의 트랜잭션과 높은 동시성 (데이터 크기는 작지만 수만 명이 동시에 요청)
			- 데이터 무결성이 생명

**인덱스 과다의 세 가지 문제**
- 저장공간 : 테이블보다 인덱스가 크면 배꼽이 배보다 커지는 격
- 쓰기 증폭 : 모든 DML이 모든 인덱스를 갱신한다
- 옵티마이저의 혼란 : 너무 많으면 잘못된 걸 선택할 확률이 오름 실행계획이 불안정해짐

**미사용 인덱스 탐지**
- MySQL 8.0(Invisible Index)
	- `ALTER TABLE orders ALTER INDEX idx_old INVISIBLE`
	- 인덱스 바로 DROP보단 옵니마이저만 안보이도록
	- 일단 숨겼다가 성능이 안좋아지면 바로 복구
	- 수일 정도 했는데 문제가 없으면 DROP
- PostgreSQL
	- `SELECT indexrelname, idx_scan FROM pg_stat_user_indexes WHERE idx_scan = 0;`
	- `pg_stat_user_indexes` 테이블에서 `idx_scan = 0` 인 거 조회
	- 인덱스에서 한 번도 안썼다를 바로 보여주는 쿼리

**MySQL vs PostgreSQL 인덱스 차이**
- InnoDB 세컨더리 인덱스 UUID PK가 위험한 이유
	- 세컨더리 인덱스의 맨 끝에 데이터를 찾아가기 위해 'PK 값'을 저장
	- PK가 가벼운 숫자면 괜찮은데 UUID처럼 36바이트 이상으로 설정하면
	- 테이블에 세컨더리 인덱스가 5개 있다면, 그 5개의 인덱스 리프 노드마다 무거운 UUID가 전부 복사되어 들어갑니다. **인덱스들의 덩치가 기형적으로 커지고, 한 페이지에 들어가는 데이터 양이 줄어들어 트리 높이가 높아지므로 검색 속도도 느려집니다**
		- 시간 순 UUID가 있다
			- 생성된 시간을 기준으로 앞부분이 정렬되는 새로운 형태의 ID (e.g. UUID v7, ULID, TSID)
- PostgreSQL HOT (Heap-Only Tuple) Update: "쓰기 증폭 방어"
	- 업데이트된 컬럼이 인덱스에 포함되지 않은 컬럼이라면, 굳이 인덱스 트리들을 건드리지 않고 진짜 데이터만 쏙 수정
- Partial Index 가성비 끝판왕 (PG 전용)
	- 보통 인덱스를 걸면 테이블의 '모든 행(Row)'을 대상으로 인덱스 트리를 만듭니다. 하지만 PostgreSQL은 조건을 걸어서 **'특정 조건을 만족하는 데이터'만 모아서 인덱스를 만들 수 있습니다.**

**면접 예상 질문**
- **복합 인덱스 (a, b, c)에서 `WHERE b = 1 AND c = 2`는 인덱스를 타나요?** → 안 탄다. **최좌측 접두사 규칙 위반.** a가 조건에 없으면 정렬 순서를 따라갈 수 없다.
- **PK를 UUID로 쓰면 어떤 문제가 있나요?** → 정렬 순서가 랜덤이라 **페이지 분할이 잦고**, InnoDB에서는 세컨더리 인덱스 리프에 PK가 들어가므로 **세컨더리 인덱스 크기가 커진다.**
- **인덱스를 추가했는데 오히려 느려진 경우가 있나요?**
	- 카디널리티가 낮아 풀 스캔보다 느린 경우 (인덱스 경유 랜덤 I/O > 순차 스캔)
	- 인덱스가 너무 많아 쓰기 성능이 떨어진 경우

**DBA 관점에서의 정리**
- 슬로우 쿼리의 90%는 인덱스로 해결된다. 하지만 **인덱스 과다의 30%는 인덱스를 줄여서 해결된다.**
- 인덱스는 정렬된 구조다. B-tree가 그 구조를 구현하고, 리프 노드의 링크드 리스트가 범위 스캔을 가능하게 한다.
	- 컬럼 순서가 중요한 이유 → **정렬 순서** 때문
	- 커버링 인덱스가 빠른 이유 → **테이블 룩업을 없앰** 때문
	- 카디널리티가 낮으면 무의미한 이유 → **옵티마이저가 더 나은 방법을 알기** 때문
