# 트랜잭션 격리 수준의 실체(+08/18)

> 📝 **Notion**: https://app.notion.com/p/3bfd7d6851ff80b59dc4cac698dacb16

> 🧩 **한 줄 요약** — 격리 수준은 "동시성 vs 정확성"을 조절하는 다이얼. 낮으면 빠르지만 이상 현상(Dirty·Non-Repeatable·Phantom)이 열리고, 높이면 락·재시도 비용이 커진다.
> **근본 원리는 MVCC의 Read View 시점** — 언제 스냅샷을 찍느냐가 격리 수준을 가른다.

---

## 1. 격리 수준 4단계

여러 트랜잭션이 동시에 처리될 때 서로 얼마나 격리되는가. 격리성이 **높을수록** 처리는 확실하지만 동시 처리가 막히고 느려진다.

| 수준 | 설명 | 특징 |
|---|---|---|
| **READ UNCOMMITTED** | 커밋 안 된 변경도 조회 가능 | 가장 낮음 · 가장 빠름 |
| **READ COMMITTED** *(Oracle·PostgreSQL 기본)* | 커밋된 변경만 조회 | 내가 접근한 행을 남이 수정 가능 |
| **REPEATABLE READ** *(MySQL 기본)* | 같은 행 조회 시 항상 같은 값 보장 | `UPDATE`/`DELETE`는 막지만 신규 `INSERT`는 못 막음 |
| **SERIALIZABLE** | 무조건 순차 처리 | 격리 최고 · 교착 확률↑ · 성능 최저 |

<details>
<summary>격리 수준은 어떻게 지정하나</summary>

- SQL: `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;`
- Spring: `@Transactional(isolation = Isolation.REPEATABLE_READ)`
- **전역이 아니라 트랜잭션 단위로 조절**하는 게 핵심 — 필요한 로직만 올린다.
</details>

## 2. 3대 읽기 이상 현상 (동시성 문제)

- **Dirty Read** — *발생: READ UNCOMMITTED*
	- 다른 트랜잭션이 수정하고 **커밋하지 않은** 데이터를 읽어버리는 상황.

		`[🖼️ 원본 이미지: Dirty Read 다이어그램]`
- **Non-Repeatable Read** (반복 불가 조회) — *발생: READ UNCOMMITTED, READ COMMITTED*
	- 한 트랜잭션 안에서 **같은 행을 2번 이상** 조회했는데 **값이 달라진** 경우.

		`[🖼️ 원본 이미지: Non-Repeatable Read 다이어그램]`
- **Phantom Read** — *발생: SERIALIZABLE 제외한 모든 수준*
	- 한 트랜잭션 안에서 **동일한 쿼리**를 보냈는데 **결과 행 집합이 달라진** 경우.

		`[🖼️ 원본 이미지: Phantom Read 다이어그램]`

| Read Uncommitted | O | O | O |

## 3. MVCC — 격리를 구현하는 원리

> 🕰️ **MVCC (Multi-Version Concurrency Control)** — 데이터의 여러 버전(스냅샷)을 두어, **락 없이** 동시성과 격리를 동시에 확보하는 기법.

- **과거 방식의 병목** — 수정 중이면 끝날 때까지 대기. 락으로 모든 충돌을 막으면 읽기가 쓰기를, 쓰기가 읽기를 막아 동시성 최악.
- **MVCC의 해법** — 스냅샷으로 과거 버전을 보존한다.
	- **읽기 트랜잭션** → 수정 중인 원본을 안 기다리고 과거 버전을 읽고 지나감.
	- **쓰기 트랜잭션** → 원본을 수정하거나 새 버전을 생성.

### 3-1. Read View — RC와 RR을 가르는 진짜 원인

MVCC가 "어느 시점 스냅샷을 보여줄지" 정하는 게 **Read View**(InnoDB의 일관된 읽기 기준). 이 **생성 시점**이 격리 수준을 가른다.

| 격리 수준 | Read View 생성 시점 | 결과 |
|---|---|---|
| **Read Committed** | **매 SELECT마다 새로** 생성 | 문장마다 최신 커밋 반영 → Non-Repeatable 발생 |
| **Repeatable Read** | **트랜잭션 첫 읽기 때 1번**, 끝까지 고정 | 항상 같은 스냅샷 → 반복 조회 결과 동일 |

> 원본이 "같은 이름, 다른 동작"이라 부른 차이의 뿌리가 바로 이 Read View 타이밍이다.

## 4. 같은 이름, 다른 동작 (MySQL vs PostgreSQL)

같은 이상 현상을 막아도 두 DB의 내부 구현은 정반대다.

### MySQL — 기본 Repeatable Read

- **쓰기** — `main`엔 최신값 덮어쓰기, 과거값은 **Undo Log**에 보관(메인이 롤백 포인터로 가리킴).
- **읽기** — 과거 시점이 필요하면 롤백 포인터를 타고 Undo Log로 가서 읽음.
- **장점** — 메인엔 최신값만 있어 테이블이 안 비대해짐.
- **단점(함정)** — 트랜잭션을 안 끝내고 오래 켜두면(Long-running) 그 스냅샷용 Undo Log를 못 지워 **디스크가 꽉 참**.
- **Phantom 방지** — 잠금 읽기·쓰기에서 행 잠금(Record Lock) + 빈 구간 잠금(Gap Lock)을 합친 **Next-Key Lock**으로 `INSERT`를 차단.
	- 대신 빈공간을 너무 많이 잠가서 대기시간이 길어지고 락끼리는 데드락의 주범이 된다
	- ⚠️ Gap Lock 탓에 **Blocking·Deadlock**이 생길 수 있다.

> 🛠️ **원본 정정** — 원본은 "RR이라 Phantom이 발생하는데 Gap Lock으로 막는다"고 적었지만, 더 정확히는 **역할이 나뉜다**: 일반 `SELECT`(스냅샷 읽기)는 **MVCC의 고정 Read View**가 이미 Phantom을 막고, `SELECT ... FOR UPDATE` 같은 **잠금 읽기·쓰기**는 **Next-Key Lock**이 막는다.

### PostgreSQL — 기본 Read Committed

- 메인 테이블(Heap)에 수정 전/후 데이터를 **나란히 물리적으로 저장**.
	- **쓰기** — 과거값을 Dead Tuple로 마킹하고 밑에 새 행을 `INSERT` → `UPDATE`가 `DELETE + INSERT`로 동작.
	- **읽기** — 스캔하며 Dead Tuple이 아닌 것만 읽음.
- **장점** — 롤백·과거 스냅샷 조회가 빠르다.
- **단점(함정)** — 업데이트가 잦으면 Dead Tuple이 쌓여 `VACUUM`으로 청소해야 함. **오래 열린 트랜잭션이 있으면 그 스냅샷에서 아직 보이는 Dead Tuple을 VACUUM이 못 지워 테이블이 부풀어 오른다**(= MySQL Undo 부풀림과 대칭).

> 🎤 **면접 한 줄** — MySQL은 빈 공간까지 물리적으로 잠그는 **비관적**(Next-Key Lock), PostgreSQL은 충돌 시 늦은 트랜잭션을 실패 처리하는 **낙관적** 방식. 그래서 트래픽이 몰릴 때 Postgres의 전체 처리량이 현저히 빠르다.

## 5. Serializable — 언제 필요한가

- **MySQL** — 모든 `SELECT`에도 `LOCK IN SHARE MODE` 급 공유 락. 읽기가 쓰기를, 쓰기가 읽기를 막음 → **데이터는 안전, 성능은 바닥.**
- **PostgreSQL** — **SSI(Serializable Snapshot Isolation)**. CCTV처럼 지켜보다 충돌이 났을 때만 취소·재시도. 평소엔 괜찮지만 충돌이 잦으면 재시도가 많아져 리소스 낭비.(재시도 로직은 개발자가 짜야함)

> 🎯 **결론** — 절대 틀리면 안 되는 로직에서만 사용 (금융 정산, 좌석 예약, 재고 차감).

## 6. 표에 없는 이상 현상 — RR도 못 막는 것

RR은 DB 레벨 반복 읽기는 보장하지만, **앱에서 읽고→계산하고→쓰는(read-modify-write)** 패턴은 못 막는다.

- **Lost Update** (갱신 손실)

	<details>
	<summary>덮어쓰기 대참사</summary>

	- 통장에 10,000원. A(나)가 10,000 읽고 +3,000 계산(13,000), 동시에 B(자동이체)도 10,000 읽고 +5,000 계산(15,000).
	- A가 "13,000 저장" → 직후 B가 "15,000 저장"으로 **A 값을 덮어씀.**
	- **결과** — A의 3,000원 증발 (18,000이어야 하는데 15,000).
	- **원인** — 둘이 '같은 초기값'을 읽고 각자 계산 뒤, 나중에 쓴 쪽이 먼저 쓴 결과를 뭉갬.
	</details>
- **Write Skew** (쓰기 왜곡)

	<details>
	<summary>눈치 게임 실패 — 둘 다 퇴근</summary>

	- 응급실엔 최소 1명 당직 필수. A, B 두 명.
	- A: "B가 있으니 난 퇴근(Update)" / 찰나에 B: "A가 있으니 나도 퇴근(Update)".
	- **결과** — 병원이 텅 비어 "최소 1명" 규칙 붕괴. 각자는 규칙을 지켰다고 믿음.
	</details>

> 🔒 위 두 현상을 막으려면 **Serializable** 이나 명시적 `SELECT ... FOR UPDATE`(비관적 락) 또는 버전 컬럼 기반 낙관적 락이 필요.

## 7. 서비스별 선택 가이드

| 도메인 | 권장 |
|---|---|
| 결제 / 정산 | Repeatable Read + `FOR UPDATE`. 성능보다 정확성 우선 |
| 일반 서비스 (주문·상품) | Read Committed로 충분. 필요한 곳만 `SELECT FOR UPDATE`로 보호 |
| 로그 / 분석 | 근사치 집계에 락 비용 불필요. 단, 서비스와 연관되면 수준을 높인다 |

## 8. DBA 관점 정리

- **MySQL DBA** — RR이 기본이니 **Gap Lock으로 인한 대기**를 항상 의식. RC로 내리면 Gap Lock은 사라지지만 Phantom이 열린다.
- **PostgreSQL DBA** — RC가 기본이니 **Non-Repeatable을 감수 중**임을 알아야 함. RR로 올리면 abort 재시도 로직이 필수.

**개념 → 한 줄 정리**

| 개념 | 한 줄 |
|---|---|
| Read View | RR은 고정 · RC는 매 문장 새로 — 반복 조회 결과가 갈리는 근본 원인 |
| Next-Key Lock | Record + Gap. MySQL RR의 잠금 읽기·쓰기가 Phantom 막는 장치 |
| MVCC | 락 없이 과거 버전 스냅샷을 읽어 동시성 확보 |
| Undo Log / Dead Tuple | 과거 버전 저장소. Long-running 트랜잭션이 있으면 부풀어 오름 |
| Lost Update / Write Skew | RR도 못 막는 앱단 read-modify-write 문제 → `FOR UPDATE` 필요 |

> ✅ **가장 중요한 것** — 운영 중인 서비스의 격리 수준이 무엇이고, 그 수준에서 무엇이 깨질 수 있는지 알고 대비하는 것.

## 🔁 셀프 체크

1. READ COMMITTED와 REPEATABLE READ의 차이를 **MVCC Read View 관점**에서 설명하라.
2. 결제 정산엔 왜 `RR + FOR UPDATE`를 쓰고, 일반 주문 조회엔 왜 RC로 충분한가?
3. MySQL RR에서 Phantom Read를 막는 건 **Gap Lock 하나뿐**인가?

<details>
<summary>답</summary>

1. RC는 매 `SELECT`마다 Read View를 새로 만들어 그때그때 최신 커밋을 보여줘 Non-Repeatable이 열리고, RR은 트랜잭션 첫 읽기 때 만든 Read View를 끝까지 고정해 같은 스냅샷을 본다.
2. 정산은 틀리면 안 되는 read-modify-write라 같은 행을 잠가(`FOR UPDATE`) Lost Update를 원천 차단해야 하고, 단순 조회는 근사 최신값이면 충분해 락 비용을 치를 이유가 없다.
3. 아니다. 스냅샷 읽기(일반 `SELECT`)는 MVCC의 고정 Read View가, 잠금 읽기·쓰기는 Record+Gap을 합친 Next-Key Lock이 막는다 — 둘이 역할을 나눈다.
</details>

<summary>📄 원본 노트 (정리 전 원문 보관)</summary>

**0. 트랜젝션 격리 수준**
- 여러 트랜잭션이 처리될 때, 트랜잭션끼리 얼마나 격리되어 있는가
	- 격리성이 클수록
		- 확실한 처리 + 동시 처리X + 속도 느려짐
	- 격리 수준 단계
		- READ_UNCOMMITED : 커밋이 되지 않은 트랜잭션의 데이터 변경을 다른 트랜잭션이 조회하는 것을 허용 (가장낮은 격리 수준 + 속도가 가장 빠름)
		- READ_COMMITTED(Oracle 기본) : 커밋이 완료된 변경사항만 조회 허용 / 어떤 트랜잭션이 접근한 행을 다른 트랜잭션이 수정 가능
		- REPEATABLE_READ(MySQL 기본) : 특정 행 조회 시 같은 데이터 응답 보장 (UPDATE/DELETE는 보장, 새 INSERT는 못 막음)
		- SERIALIZABLE : 무조건 순차 진행 / 격리성 최고 / 교착상태 확률 높고 성능 최저

**1. 격리수준에 따라 발생 가능한 3대 읽기 이상 현상**
- Dirty Read (READ_UNCOMMITED) : 다른 트랜잭션이 수정하고 커밋 안 한 데이터를 읽을 수 있는 상황 (이미지: Dirty Read 다이어그램)
- Non-Repeatable Read (Read Committed, Read Uncommitted) : 한 트랜잭션 내 같은 행 2번 이상 조회했는데 값이 다른 경우 (이미지: Non-Repeatable Read 다이어그램)
- Phantom Read (Serializable 제외 전부) : 동일 쿼리인데 조회 결과가 다른 경우 (이미지: Phantom Read 다이어그램)
- 표 : RU(O/O/O) · RC(X/O/O) · RR(X/X/O) · Serializable(X/X/X)

**2. MVCC — 격리를 구현하는 방법**
- 과거 : 수정 중이면 대기 → 트래픽 몰리면 병목 → 락으로 다 막으면 읽기/쓰기 서로 막음(동시성 최악)
- MVCC : 다중 접근 가능 + Lock 없이 동시성 제어
- 동작원리 : 데이터 스넵샷을 찍음(이전 버전 보존) / 읽기=과거 버전 읽고 지나감 / 쓰기=원본 수정이나 새 버전 제작

**3. 같은 이름, 다른 동작**
- MySQL - Repeatable Read : 쓰기(main 덮어쓰기 / Undo Log 과거데이터·롤백포인터) / 읽기(롤백포인터 타고 Undo Log 읽음) / 장점(메인 안 비대) / 단점(Long-running이면 Undo Log 못 지워 디스크 꽉참) / 기본 RR이라 팬텀 가능한데 Gap Lock으로 INSERT 차단 → Gap Lock 때문에 Blocking 발생 가능
- PostgreSQL - Read Committed : Heap에 수정 전/후 나란히 저장 / 쓰기=과거를 Dead Tuple 마킹하고 새 행 INSERT(UPDATE=DELETE+INSERT) / 읽기=Dead Tuple 아닌 것만 / 장점(롤백·과거조회 빠름) / 단점(Dead Tuple 많아지면 VACUUM) / 기본 RC라 SELECT 결과 다를 수 있음(Non-Repeatable), 암묵적 락 범위 줄이고 동시성 극대화 위해 사용
- 면접에서는? MySQL=Gap Lock으로 빈 공간 물리적 잠금(비관적) / PostgreSQL=늦은 트랜잭션 실패 처리(낙관적), 트래픽 몰릴 때 처리량 현저히 빠름

**4. Serializable — 언제 필요한가**
- MySQL : 모든 SELECT도 SELECT ... LOCK IN SHARE MODE 공유 락 → 읽기가 쓰기 막고 쓰기가 읽기 막음(데이터 안전, 성능 바닥)
- PostgreSQL : SSI(Serializable Snapshot Isolation) 감시 시스템, 충돌 시만 취소·재시도, 충돌 잦으면 재시도 많아져 리소스 낭비
- 결론 : 절대 틀리면 안 되는 로직에 필요(금융 정산, 좌석 예약, 재고 차감)

**5. 표에 없는 이상 현상**
- Repeatable Read의 한계
	- Lost Update(덮어쓰기 대참사) : 통장 10,000 / A 3,000 입금 계산(13,000), B 5,000 입금 계산(15,000) / A 저장 후 B가 덮어씀 → A의 3,000 증발(18,000이어야 하는데 15,000) / 원인=같은 초기값 읽고 각자 계산 뒤 나중에 쓴 쪽이 뭉갬
	- Write Skew(눈치게임 실패) : 응급실 최소 1명 필수, A/B 서로 상대 있으니 나 퇴근 처리 → 둘 다 퇴근 → 규칙 붕괴
	- 위 이상현상 막으려면 Serializable이나 명시적 FOR UPDATE 필요

**6. 서비스별 선택**
- 결제/정산 : Repeatable Read + FOR UPDATE. 성능보다 정확성 우선
- 일반 서비스(주문·상품) : Read Committed로 충분, 필요한 곳만 SELECT FOR UPDATE
- 로그/분석 : 근사치 집계에 락 비용 불필요, 서비스와 연관되면 수준 높이기
- 격리 수준은 전역이 아니라 트랜잭션 단위로 조절

**7. DBA 관점에서의 정리**
- MySQL DBA : RR 기본이니 Gap Lock 대기 항상 의식. RC로 내리면 Gap Lock 사라지나 Phantom 열림
- PostgreSQL DBA : RC 기본이니 Non-Repeatable 감수 중임을 인지. RR로 올리면 abort 재시도 로직 필수
- 중요한 건 운영 중 서비스의 격리 수준이 뭔지 알고 그 수준에서 뭐가 깨질 수 있는지 대비하는 것
</details>

<summary>추가정리(08/18) - 읽기 성능이 압도적일 때 왜 PostgreSQL가 상대적으로 불리한가?</summary>

1. Heap + Index : B-Tree를 타도 TID를 찾아 Heap 영역을 한 번 더 방문해야해서 Clustered 방식인 MySQL보다 디스크 접근이 많다(느리다)
2. MVCC가 새버전 추가 + Dead Tuple 남기기 방식이라 쓰기가 많아지면 공간 비대 + 읽을 때 일일히 확인 해야함 → 오버헤드 발생(느려짐)
3. Read Replica :<br>MySQL : Binlog기반 → 마스터에 부하없이 슬래이브를 늘리기 쉽다 <br>PostgreSQL : WAL(Write-Ahead Log) 기반<br>마스터와 슬레이브가 디스크 블록 단위로 똑같아야 함<br>+ 마스터에서 Vacuum시 슬레이브에서도 해당 물리적 블록을 지워야 함<br>만약 슬레이브에서 누군가 긴 `SELECT` 쿼리를 실행 중인데 마스터에서 지시가 내려오면, 쿼리를 강제 취소시키거나(쿼리 실패), 마스터의 업데이트를 지연시키는 충돌이 발생
4. 커버링 인덱스<br>MySQL : Secondary에 찾고자 하는 데이터와 PK가 모두 있다면, 실제 테이블에 접근하지 않고 **인덱스만 읽고 끝냅니다**<br>PostgreSQL : **MVCC** 에서 인덱스에 있는 데이터가 '살아있는 데이터'인지 인덱스만 봐서는 알 수 없음<br>그래서 **Visibility Map**(이 페이지의 데이터는 모두 유효함 등을 기록한 맵)을 사용하는데 Vacuum이 제때 돌지 않아 맵이 갱신되지 않았다면 **결국 Heap 테이블을 또 뒤져서** 버전을 확인해야 합니다. 즉, 완벽한 커버링 인덱스가 보장되지 않습니다
5. 단순 쿼리 처리량<br>MySQL : 스래드 기반 → 쿼리과정이 매우 짧다<br>PostgreSQL : 프로세스 기반 → 연결마다 프로세스 할당 (복잡+무거운 쿼리 처리를 위한 무거운 옵티마이저가 있어 상대적으로 오버헤드 발생 )<br>즉, 멀티 스레드와 멀티 프로세스 구조로 인한차이
