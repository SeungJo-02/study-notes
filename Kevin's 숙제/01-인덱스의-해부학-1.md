## 1. B-Tree — 거의 모든 인덱스의 기본

"Balanced Tree". 모든 리프 노드의 깊이가 같다. **1000만 행이어도 루트→리프가 보통 3~4단계.**
`CREATE INDEX`를 옵션 없이 쓰면 MySQL·PostgreSQL 모두 B-Tree가 만들어진다. `=`, `<`, `>`, `BETWEEN`, `ORDER BY` — 범위 검색과 정렬에 모두 쓸 수 있어 만능에 가깝다.

<details>
<summary>여기서의 B-Tree는 B+Tree이다.</summary>

B-Tree
- 모든 노드에 데이터가 들어가 있다
	- 즉, 키와 데이터가 같이 들어가 있어 한 노드에 차수가 적게 들어간다<br>한 노드에 들어갈 수 있는 크기가 정해져 있는데 데이터는 크기가 크다
	- 그러면 높이가 커지고 그러면 I/O 가 많아진다라는 단점

B+Tree
- 리프 노트에만 데이터가 들어가 있다
	- 뿌리 및 중간노드는 데이터는 없고 키(방향키)만 존재하고 데이터는 가장 밑 리프노드에만 있다
		- 그러면 한 노드에 차수가 많이 들어갈 수 있어 트리 높이가 작아져 I/O 횟수가 떨어짐→성능up
	- 단건 검색은 B-Tree랑 큰 차이가 없고 운이 좋으면 B-Tree가 더 빠름<br>대신 범위 검색은 B+Tree는 가장 밑 노드끼리 이어져 있기에 더 빠름 (전자는 위아래 왔다갔다)
</details>

## 2. 저장 구조의 차이

|  | **InnoDB — Clustered Index** | **PostgreSQL — Heap + Index** |
|---|---|---|
|  | 국어사전 (찾는 단어 옆에 뜻이 적혀있) | 전공서적(index에서 페이지 번호 차고 본문으로 이동) |
|  | PK 순서대로 데이터가 정렬되어 저장 | 순서 상관 없이 마구잡이로 집어 던져 놓는다(Heap) 리프노드에 찐 데이터가 없고 Heap에 몇 번 노드에 있는지 알려주는 주소(TID)만 적혀있다 |
| 장 | 회원번호(PK)찾으려고 내려가면 이름,나이,주소 등 데이터가 있다 | 삽입/업데이트 속도가 최고 |
| 단 | 중간에 데이터가 끼어들면 노드를 쪼개야하는 작업 발생<br>즉, 삽입/수정이 무거움 | 리드 노드의 주소를 얻고 Heap으로 한 번 더 찾아가야하는 수고가 발생 |
|  | PK 위주로 빠르게 데이터를 읽어내야할 때 유리 | 데이터 삽입/업데이트/ 다양한 조건의 검색에 유리 |

- 두 DB는 B+Tree를 만들지만 가장 밑에 뭘 넣을 건가가 차이다

## 3. B-Tree 외의 인덱스

|  | Hash | GIN(Generalized Inverted Index) | Gist(Generalized Search Tree) |
|---|---|---|---|
| 요약 | 정확한 일치만 제일 빠르게 | Index 페이지 같은 느낌 | 유제품 구역에 우유코너에 딸기우유 … |
| 원리 | 데이터를 해시로 바꾸고 그 위치에 박아 | B+Tree : 1번 문서에 A가 있다<br>GIN : A는 1번,2번 문서에 있다고 저장 | 좌표나 면적 데이터를 위한 인덱싱<br>데이터를 서로 겹치거나 포함되는 테두리 상자로 묶어 트리를 만듬 |
| 장 | 정확한 일치는 B+Tree보다 빠름 | 풀텍스트 검색(게시글에서 특정 단어 검색)<br>JSON 데이터 내부의 특정 Key값 찾기 등<br>덩어리에서 뭔가를 뽑아 낼 때 유리 | 공간 지리 데이터 처리 시 절대적 필요<br>B+Tree :는 2차원이 안됨 |
| 단 | 범위 검색이 완전 불가 |  |  |

## 4. Covering Index

- 쿼리를 쳤는데 마침 쿼리의 검색 조건과 가져올 데이터가 모두 인덱스 안에 있어서<br>DB를 안 찍어도 된다! → I/O 디스크 줄어든다
-

	| MySQL | PostgreSQL 11+ (INCLUDE) |
	|---|---|
	| CREATE INDEX idx ON orders(user_id, status, amount); | CREATE INDEX idx ON orders(user_id) INCLUDE (status, amount); |
	| 쿼리 : 인덱싱을 하나만 이용해도 다른 인덱싱 된 컬럼까지 사용한다<br>즉, user_id만 사용해도 다른 컬럼까지 인덱싱 사용 | 중간 노드에 찐으로 쓸 컬럼만 적어두기<br>리프노드에 도착하면 덤으로 다른 컬럼들까지 인덱싱 가능 하도록 함<br>즉, 인덱싱된 컬럼으로 먼저 데이터를 찾아낸 뒤 → 그 결과 안에서 INCLUDE된 컬럼 데이터의 데이터를 검사 혹은 사용 |
	| 그러다 보니 노드 하나에 들어갈 표지판 수(차수)가 줄고 트리 높이가 길어짐<br>인덱싱 성능은 up, I/O 성능은 떨어짐 | 대신 처음부터 INCLUDE에 있는 컬럼은 풀스캔이다<br>즉, 별도의 인덱싱을 해야 함 |

## 5.  Cardinality와 Selectivity

- Cardinality : 컬럼에 있는 값 개수
- Selectivity : 1/ Cardinality
- 즉 Cardinality 수는 클수록, Selectivity는 작을 수록 좋다
- Cardinality가 낮으면 결국 절반을 읽게 되는데<br>인덱스는 또 I/O를 발생 시킨다 즉, Cardinality가 작으면 풀스캔 만 못하다

## 6. 복합 인덱스의 순서  — Leftmost Prefix Rule

- 복합 인덱스 만들 때 인덱스의 맨 왼쪽 컬럼부터 끊김 없이 차례대로 사용해야만 인덱스를 탈 수 있다는 규칙
	- e.g. [본부, 팀, 이름] 이렇게 복합인덱스를 걸면
		- 되는 경우
			- WHERE 본부 = '영업본부'
			- WHERE 본부 = '영업본부' AND 팀 = '해외팀'
			- WHERE 본부 = '영업본부' AND 팀 = '해외팀' AND 이름 = '김철수'
		- 안되는 경우
			- WHERE 팀 = '해외팀'
			- HERE 본부 = '영업본부' AND 이름 = '김철수'
- 즉, 복합 인덱스 만들었다면? 검색 조건에 A는 가장 먼저 필수로 나와야 함
- 만약 안되는 경우 사용 시 풀스캔이다 <br>그니까 설계를 잘하자
