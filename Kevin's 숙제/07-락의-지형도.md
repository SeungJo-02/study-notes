# 락의 지형도 — Row Lock, Gap Lock, Advisory Lock

> 📝 **Notion**: https://app.notion.com/p/3c1d7d6851ff8045b486e258481faf81

## 0. 왜 락이 필요한가

- 잔액 10,000원. A가 7,000원, B가 5,000원을 동시에 인출한다. 락 없이 둘 다 10,000원을 읽고 각자 차감하면 **둘 다 성공하고 잔액은 -2,000원이 된다.**
- 위 문제를 막기 위해 락을 사용하고 락은 동시접근을 직렬화해서 데이터의 접합성을 지켜준다.<br>(속도는 느려지지만)

## 1. Shared Lock vs Exclusive Lock

- 모든 DB 락의 기본 분류
- Shared Lock(S)
	- 읽기 트랜잭션이 진행 중일 때 다른 읽기 트랜잭션은 허용해준다.
	- 읽기 트랜잭션이 진행 중일 때 다른 쓰기 트랜잭션을 허용하지 않는다.
	- 즉, 여러 트랜잭션이 동시에 잡을 수 있다.
- Exclusive Lock(X)
	- 한 트랜잭션이 진행 중일때 그 어떤 트랜잭션도 들어오지 못한다
	- 즉, 하나만 잡을 수 있다.

## 2. InnoDB의 Row Lock — 인덱스가 곳 락 범위다

- InnoDB는 **인덱스 기반**으로 행 잠금을 건다.
- 인덱스가 없으면 Clustered 인덱스(PK)를 전부 스캔하면서 락을 건다(사실상 테이블 락)
	- 인덱스 X : 한 번 쓰기 트랜잭션이 발동되면 테이블 전체에 락이 걸려 속도가 느려짐
	- 인덱스 O : 인덱싱 된 컬럼만 잠기니까 레코드(행)락이 발동됨

## 3. Gap Lock과 Next-Key Lock([전 장 보기](https://app.notion.com/p/3c1d7d6851ff8010b0e2ced8379c7051))

- Gap Lock : **행과 행 사이의 빈 공간** 잠금<br>팬텀리드 막으려고 사용
- **Next-Key Lock(**Row Lock + Gap Lock.**) :** InnoDB의 기본 잠금 단위
- 보통 팬텀 리드를 막으려면 SERIALIZABLE까지 트랜잭션 격리 수준을 올려야하는데 너무 느리다는 단점 존재<br>MySQL : RR + Next-Key Lock으로 팬텀 리드를 막음
- 추가
	- READ COMMITTED로 트랜잭션 격리수준을 내리면 **Gap Lock이 사라진다.** (Non-Repeatable Read와 팬텀 리드 현상을 모두 허용하는 스펙이기에 )

## 4. PostgreSQL — MVCC와 명시적 락

- PostgreSQL은 락 대신 **MVCC**로 읽기/쓰기 충돌을 피한다.([참고](https://app.notion.com/p/3bfd7d6851ff80b59dc4cac698dacb16))
	- 행 수정 시 이전버전은 Dead Tuple로 표시 후 나중에 VARCUUM으로 제거하는 방식
	- MVCC가 충돌을 피해줘도 **쓰기끼리는 여전히 락이 필요하다.**

		| 구문 | 락 | 용도 |
		|---|---|---|
		| `FOR SHARE` | S Lock | 읽는 동안 변경 방지 |
		| `FOR UPDATE` | X Lock | 수정 예정 |
		| `FOR NO KEY UPDATE` | 약한 X | PK/Unique 외 컬럼 수정 시 |
		| `FOR KEY SHARE` | 약한 S | FK 참조 시 |
- 즉, MySQL 이든 PostgreSQL이든 읽기는 MVCC로 충돌을 피하고 쓰기는 Lock으로 충돌을 피함<br>MySQL : **Next-Key Lock**<br>PostgreSQL : 세분화된 락 모드

## 5. Advisory Lock — 사용자 정의 락

- Advisory Lock : 물리적 락이 아님<br>DB 안의 데이터를 보호하려는 목적이 아닌<br>외부 API 중복 호출 방지등 백엔드 서버의 **비즈니스 로직흐름을 통제**하기 위해 DB의 락 기능만 잠시 빌려 쓰는 것
- DB 서버의 **메모리 공간에 논리적인 이름표를 달아두는 것**
- e.g. "내가 '12345'라는 이름의 회의실 열쇠를 먼저 가져갈 테니, 다른 서버가 이 열쇠를 찾으면 내가 반납할 때까지 기다리라고 해줘"

	```javascript
	-- PostgreSQL
	SELECT pg_advisory_lock(12345);
	-- ... 작업 ...
	SELECT pg_advisory_unlock(12345);

	-- MySQL
	SELECT GET_LOCK('my_lock', 10);
	-- ... 작업 ...
	SELECT RELEASE_LOCK('my_lock');
	```
- 배치 중복 실행 방지
- 분산 환경의 리더 선출
- 외부 리소스 접근 제어
- **테이블 락이나 인덱스와 전혀 무관**하기 때문에 **쿼리 성능에 영향을 주지 않는다**

## 6. 데드락

- A가 행 1을 잠그고 행 2를 기다리고, B가 행 2를 잠그고 행 1을 기다리는 상황
- **MySQL** — InnoDB가 감지 즉시 하나를 롤백. 보통 **작업량이 적은 쪽을 희생**
- **PostgreSQL** — `deadlock_timeout`(기본 1초) 이후 감지해서 하나를 취소
- **데드락을 줄이는 방법**
	1. **접근 순서 통일** — 항상 PK 오름차순으로 접근. A와 B가 같은 순서로 잠금면 데드락이 발생하지 않는다
	2. **트랜잭션을 짧게** — 트랜잭션 안에서 외부 API 호출 같은 느린 작업을 하지 않는다
	3. **적절한 인덱스** — 인덱스가 없으면 락 범위가 넓어져 불필요한 행까지 잠근다

## 7. 메타데이터 락 (MDL)

- MySQL에서 DDL과 DML이 충돌할 때 걸리는 락
- 누군가 SELECT를 하고 있으면 `ALTER TABLE`이 대기하고, ALTER가 대기하면 **그 이후의 모든 SELECT도 대기**
	- `ALTER TABLE`은 이미 만들어져 있는 테이블의 **'구조(뼈대)를 고치는'** 명령어
- 줄서기 효과
	- 트랜잭션 A : 평범한 `SELECT` 쿼리를 실행 → MDL 읽기 락 획득
	- 트랜잭션 B : 컬럼을 추가하려고 `ALTER TABLE`을 실행 → MDL 쓰기 락 요청
	- 트랜잭션 C : 0.01초면 끝나는 아주 가벼운 `SELECT` 쿼리를 실행(대기)
		- DDL : 테이블을 조작하는 것
			- CREATE : 새 테이블 추가
			- ALTER : 컬럼 추가/변경, 인덱스 달기
			- DROP : 테이블 삭제 등등
		- DML : 데이터 조작하는 것
			- `INSERT, UPDATE, DELETE, SELECT`

## 8. 락 모니터링

```javascript
-- MySQL
SELECT * FROM performance_schema.data_locks;
SELECT * FROM sys.innodb_lock_waits;

-- PostgreSQL
SELECT * FROM pg_locks;
SELECT * FROM pg_stat_activity WHERE wait_event_type = 'Lock';

DBA의 순서 —

1. **어떤 세션이 잡고 있는가?**
2. **그 세션은 뭔 하고 있는가?**
3. **그 세션을 죽여도 되는가?**
```

## 9. 낙관적 락 vs 비관적 락

- 비관적
	- **금융처럼 충돌 비용이 큰 시스템**
- 낙관적
	- **읽기가 많고 충돌이 드물 때**

## 10. 마무리

- 락은 데이터를 지키는 장치이면서 성능을 떨어뜨리는 원인
	- InnoDB의 **Gap Lock**은 팬텀 리드를 막지만 예상치 못한 대기를 치름
	- PostgreSQL의 **MVCC**는 읽기/쓰기 충돌을 없애지만 **VACUUM**이라는 대가를 치름
- 락 문제를 풀 때 가장 중요한 것
	- **누가 잡고 있는가를 빠르게 찾는 것**
	- 쿼리가 느린 게 아니라 **기다리고 있는 것**일 수 있다.
	- **트랜잭션은 짧게, 접근 순서는 일정하게, 인덱스는 정확하게.**
