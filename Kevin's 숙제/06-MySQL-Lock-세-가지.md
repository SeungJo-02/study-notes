# MySQL Lock 세 가지 — 레코드 락, 갭 락, 넥스트 키 락

> 📝 **Notion**: https://app.notion.com/p/3c1d7d6851ff8010b0e2ced8379c7051

> 🔒 **한 줄 요약** — MySQL(InnoDB)은 REPEATABLE READ에서 **잠금 읽기**의 Phantom Read까지 막으려고, 기존 행을 지키는 **레코드 락**과 빈 틈을 지키는 **갭 락**을 합친 **넥스트 키 락**을 쓴다. 단, 이 락들은 `FOR UPDATE`류 잠금 읽기·쓰기에서만 작동하고 일반 `SELECT`는 MVCC로 처리된다.

---

## 1. 배경 — 왜 이 락들이 필요한가

MySQL 기본 격리 수준은 **REPEATABLE READ**. 표준대로면 Phantom Read가 열리지만, InnoDB는 **넥스트 키 락**으로 잠금 읽기에서 그것까지 방어한다.

| 방어 대상 | 무엇을 보호하는가 |
|---|---|
| Non-Repeatable Read | 내가 읽은 **기존 데이터가 수정/삭제**되지 않게 보호 → **레코드 락** |
| Phantom Read | 내가 읽은 **범위 사이에 새 데이터가 끼어들지** 못하게 보호 → **갭 락** |

- 이 둘을 각각 레코드 락·갭 락이 막고, **둘을 묶은 것이 넥스트 키 락**이다.
- 락은 **인덱스**에 걸린다(행이 아니라 인덱스 레코드). 예시: 인덱스에 `id = 10, 20, 30`이 있다고 두고 아래를 읽는다.

---

## 2. 레코드 락 (Record Lock)

- **잠금 대상** — 인덱스의 **행(레코드) 하나**.
- **잠금 범위** — `[20, 20]` (20번 레코드만).
- **역할** — 내가 잡은 20번을 다른 트랜잭션이 **UPDATE/DELETE 못 하게** 막음.
- **한계** — 레코드 사이 빈 공간에 새 행이 **INSERT되는 건 못 막음**.

## 3. 갭 락 (Gap Lock)

- **잠금 대상** — 레코드와 레코드 **사이 빈 간격**.
- **잠금 범위** — `(10, 20)` (11~19 빈 공간).
- **역할** — 그 구간에 다른 트랜잭션이 **INSERT하는 걸 원천 차단**(Phantom 방지).
- **특이사항** — 양 끝 레코드(10, 20) **자체는 못 막음**. 또 갭 락끼리는 **서로 충돌하지 않아** 여러 트랜잭션이 같은 갭을 동시에 잠글 수 있다(INSERT만 막을 뿐).

## 4. 넥스트 키 락 (Next-Key Lock)

- **잠금 대상** — 갭 락 **+** 레코드 락.
- **잠금 범위** — `(10, 20]`.
- **역할** — `11~19`는 갭 락(INSERT 차단), `20`은 레코드 락(UPDATE/DELETE 차단).

```sql
-- id 인덱스에 10, 20, 30이 있을 때
SELECT * FROM t WHERE id BETWEEN 10 AND 20 FOR UPDATE;
-- → 20에 레코드 락 + (10,20) 갭 락 = 넥스트 키 락 (10,20]
--   (범위 끝 다음 갭 (20,30)까지 잠기는 경우도 많다)
```

---

## 5. 한눈에 비교 & 언제 걸리나

| 락 | 잠금 범위 | INSERT 차단 | UPDATE/DELETE 차단 |
|---|---|---|---|
| 레코드 락 | `[20, 20]` | ❌ | ✅ |
| 갭 락 | `(10, 20)` | ✅ | ❌ |
| 넥스트 키 락 | `(10, 20]` | ✅ | ✅ |

> 🎯 **언제 걸리나 (원본 "질문"의 정확한 답)** — 이 락들은 **잠금 읽기·쓰기**(`SELECT ... FOR UPDATE`/`FOR SHARE`, `UPDATE`, `DELETE`)에서만 걸린다. 일반 `SELECT`는 락 없이 **MVCC 스냅샷**으로 읽는다. 그래서 "갭 락만 쓰면 되지 않나?"의 답은 → **읽기(스냅샷)는 MVCC가 처리하지만, 쓰기에서 기존 행 보호(Non-Repeatable 방지)는 격리 수준만으론 안 되므로 레코드 락까지 합친 넥스트 키 락이 필요**하다.

## 6. 실무 함정 & 셀프 체크

> ⚠️ **인덱스가 락의 전부다** — 조건 컬럼에 **인덱스가 없으면** InnoDB가 풀스캔하며 **훑은 모든 행과 갭을 잠가** 사실상 테이블 전체가 잠긴다. 반대로 **유니크 인덱스 등호**(`WHERE id = 20`)로 정확히 한 행을 찾으면 갭 락 없이 **레코드 락만** 건다. 또 **READ COMMITTED**로 내리면 갭 락이 (거의) 비활성화되어 Phantom이 다시 열린다.

### 🔁 셀프 체크

1. 레코드 락·갭 락·넥스트 키 락의 **잠금 대상과 범위**를 각각 말하라.
2. 왜 **갭 락만으로는 부족**하고 넥스트 키 락이 필요한가?
3. 이 락들이 **안 걸리는 경우**는? 인덱스 없는 컬럼으로 조건을 걸면 어떻게 되나?

3. 일반 `SELECT`(MVCC 스냅샷)엔 안 걸리고 잠금 읽기·쓰기에서만 걸린다. 인덱스 없는 컬럼으로 조건을 걸면 풀스캔한 모든 행·갭을 잠가 테이블 전체가 잠기다시피 한다.

<summary>📄 원본 노트 (정리 전 원문 보관)</summary>

**0. 배경 — 왜 이 Lock들이 필요한가**
- MySQL은 REPEATABLE READ 격리 수준이라 팬텀 리드라는 문제점이 발생 → 그래서 Next-Key Lock이라는 기법으로 Phantom Read까지 방어
	- 방어 대상 / 무엇을 보호하는가
	- Non-Repeatable Read : 기존 = 읽고 있던 데이터의 변경 가능성 존재 / 내가 읽은 기존 데이터가 수정·삭제되지 않게 보호
	- Phantom Read : 기존 = 읽고 있던 데이터의 추가 행 발생 가능성 존재 / 내가 읽은 범위 사이에 새로운 데이터가 끼어들지 못하게 보호
- 위 두 가지를 각각 레코드 락과 갭 락으로 막을 수 있고 둘을 묶은 것이 넥스트 키 락이다.

**1. 레코드 락 (Record Lock)**
- 잠금 대상 : 테이블의 인덱스 행 데이터
- 잠금 범위 : [20, 20] (20번 레코드만 잠금)
- 핵심 역할 : 내가 20번 데이터를 잡고 있을 때 다른 트랜잭션이 들어오지 못하게 막아줌
- 한계 : 나머지 데이터의 빈공간에 새로운 데이터가 INSERT되는 건 못막음

**2. 갭 락 (Gap Lock)**
- 잠금 대상 : 레코드와 레코드 사이 빈 간격(10번 데이터 ~20번 데이터 사이)
- 잠금 범위 : (10, 20) (11번~19번 사이 빈공간 잠금)
- 핵심 역할 : 해당 공간에 다른 트랜잭션이 새로운 데이터 INSERT 하는 걸 원천 차단
- 특이사항 : 양 끝(10번, 20번) 레코드 자체는 못막는다

**3. 넥스트 키 락 (Next-Key Lock)**
- 잠금 대상 : 갭 락 + 레코드 락
- 잠금 범위 : (10, 20]
- 핵심 역할 : 11~19는 갭 락(INSERT 차단), 20은 레코드 락(UPDATE/DELETE 차단)

**정리**
- 레코드 락 : INSERT 차단 ❌ / UPDATE·DELETE 차단 ✅
- 갭 락 : INSERT 차단 ✅ / UPDATE·DELETE 차단 ❌
- 넥스트 키 락 : INSERT 차단 ✅ / UPDATE·DELETE 차단 ✅

**질문**
- MySQL에서 갭 락만 사용하면 되는 거 아니에여?
	- 읽기에서는 맞는 말인데 쓰기는 동시성문제를 트랜잭션 격리수준에서 막아주지 못하기 때문에 넥스트 키 락을 사용해야함
</details>
