> 🧩 **한 줄 요약** — 데이터·인덱스가 그대로인데 같은 쿼리가 어제 0.01초, 오늘 30초가 되는 건 대부분 **옵티마이저가 통계를 보고 실행계획을 바꿨기** 때문. 이 문서는 옵티마이저가 *무엇을 보고, 왜 틀어지고, 어떻게 되돌리는지*를 다룬다.

---

## 1. 옵티마이저와 비용 기반 최적화

- 옵티마이저 = SQL이 원하는 데이터를 **가장 빠르게 가져올 실행 경로**를 고르는 DB 엔진
- 현대 DB는 전부 **CBO (Cost-Based Optimizer)** — 여러 실행계획의 비용을 추정해 가장 낮은 걸 선택
- 여기서 비용은 실제 실행시간이 아니라 **추정치**다. 추정의 근거 = **통계 정보**

> ⚠️ 그래서 **통계가 낡으면 판단이 틀어진다.** 이것이 위 오프닝 문제(어제 0.01초 → 오늘 30초)의 범인이다.

---

## 2. 통계 정보와 히스토그램

**통계 정보** = 옵티마이저가 참고하는 데이터 요약본: 행 수, 카디널리티, 히스토그램, NULL 비율, 인덱스 선택도(selectivity).

- **ANALYZE** — 데이터가 추가·삭제되어 통계가 낡으면 갱신하는 명령. CPU·메모리를 꽤 써서 **트래픽 적은 새벽**에 돌리는 게 좋다.

### 2-1. 히스토그램이 왜 필요한가

> 💡 카디널리티(값 종류 수)만 알면 "값이 2종류니 50:50이겠지"로 추정한다. 실제 분포가 **99:1**이면 크게 빗나간다. **히스토그램은 값의 실제 분포**를 담아, 1% 값엔 인덱스·99% 값엔 풀스캔을 고르게 해준다.

---

## 3. 실행계획 읽기 (EXPLAIN)

### 3-1. MySQL vs PostgreSQL 스캔 방식 매칭

| 스캔 방식 | MySQL `type` | PostgreSQL |
|---|---|---|
| Index Seek | `const` `eq_ref` `ref` | Index Scan |
| Index Range Scan | `range` | Index Scan (범위) |
| 인덱스 풀스캔 | `index` | — |
| 풀스캔 | `all` | Seq Scan |
| 인덱스+풀스캔 중간 | (없음) | Bitmap Scan |

- MySQL은 `EXPLAIN` 결과의 `type` `key` `rows` `Extra`를 본다. **`type`이 가장 중요.**
- `rows` = 옵티마이저가 예상한 읽을 행 수(추정치). `ANALYZE TABLE`로 최신화가 중요. `EXPLAIN ANALYZE`는 실제 실행해 **찐 시간**을 보여준다.
- **Bitmap Scan (PG)** — 인덱스로 조건에 맞는 행들의 힙 주소(TID)를 싹 모아 **물리적 페이지 순서로 정렬한 지도**를 만든 뒤 읽는다. 디스크 헤드가 널뛰는 랜덤 I/O를 순차에 가깝게 줄인다.

### 3-2. JOIN 전략 3가지

| 전략 | 방식 | 언제 유리한가 |
|---|---|---|
| Nested Loop | A를 한 행씩 읽으며 그때마다 B를 뒤져 짝 맞춤 | 소량 + B 조인 컬럼에 인덱스가 있을 때 |
| Hash Join | 작은 테이블로 해시 사전을 만들고 큰 테이블을 훑으며 매칭 | 대용량. 인덱스 없어도 효율적 |
| Merge Join | 두 테이블을 조인 컬럼으로 각각 정렬해두고 병합 | 대량 + 정렬돼 있거나 정렬 가능할 때 |

- **MySQL** — 원래 Nested Loop만. **8.0.18부터 Hash Join** 추가. Merge Join 없음.
- **PostgreSQL** — 3가지 모두 지원 + 서브쿼리 최적화. 정기 ANALYZE 필요.

## 4. 실행계획이 갑자기 바뀌는 이유

어제는 빨랐는데 오늘 느려졌다면 아래 4가지를 의심한다.

- **통계 갱신** — 새벽 자동 `ANALYZE`로 통계 장부가 바뀌면 옵티마이저 판단도 바뀐다.
- **데이터 분포 변경** — VIP가 1%였다가 이벤트로 70%가 되면, Table Lookup 대신 풀스캔을 고른다.
- **테이블 크기 변화** — 작을 땐 풀스캔이 더 빠르고, 커지면 인덱스 계획으로 전환된다.
- **버전 업그레이드** — 옵티마이저 알고리즘이 바뀐다 → 업그레이드 후 **회귀 테스트** 필요.

<details>
<summary>⚠️ 실무 함정 — Parameter Sniffing (바인드 변수 값에 계획이 물림)</summary>

- DB는 쿼리를 처음 실행할 때의 **바인드 변수 값**으로 실행계획을 짜서 캐시해둔다.
- 그 첫 값이 희귀 값(1%)이면 "인덱스 타자" 계획이 캐시되는데, 이후 흔한 값(70%)으로 같은 쿼리를 날리면 그 계획이 오히려 독이 된다.
- **"같은 쿼리, 다른 속도"의 또 다른 흔한 범인.** SQL Server·Oracle에서 특히 유명하고, MySQL/PG도 프리페어드 스테이트먼트에서 겪는다.
</details>

## 5. 힌트와 쿼리 리라이팅

**힌트** — 통계가 부정확할 때 "이 인덱스 타라"고 강제하는 기능. 쿼리 주석으로 지시한다.

```sql
-- MySQL: 인덱스 강제
SELECT /*+ INDEX(orders idx_user) */ *
FROM orders WHERE user_id = 42;

-- PostgreSQL (pg_hint_plan)
/*+ IndexScan(orders idx_user) */
SELECT * FROM orders WHERE user_id = 42;
```

> 🚫 **힌트는 최후의 수단.** 데이터가 바뀌면 고정된 힌트가 오히려 독이 된다. 통계 갱신(`ANALYZE`)이나 인덱스 재설계가 항상 우선이다.

**쿼리 리라이팅** — 결과가 같아도 다르게 쓰면 옵티마이저가 다른 계획을 짠다.

- 특히 **MySQL은 서브쿼리(`IN`) 해석이 약해**, 바깥·안쪽 테이블을 반복해서 도는 최악 계획을 짤 때가 많다.
- `IN` 서브쿼리를 **JOIN으로 바꾸면** Hash Join·Merge Join 같은 고급 전략을 쓸 수 있다.

## 6. Adaptive Query Optimization (AQO)

- **기존** — 실행 **전**에 계획을 확정. 통계가 틀리면 그대로 느려진다.
- **적응형** — 실행 **도중** 막히면 실시간으로 경로를 바꾼다.
- **Oracle 12c (Adaptive Plan)** — Nested Loop을 쓰다 너무 느리면 Hash Join으로 전환.
- **MySQL 8.0** — AQO 없음. (Hash Join이 추가된 정도)

> 🛠️ **정정 — PostgreSQL의 JIT은 적응형 최적화가 아니다.** JIT은 실행계획을 도중에 바꾸는 게 아니라, 무거운 쿼리의 식·조건을 실행 시점에 **기계어로 컴파일**해 CPU 계산을 빠르게 하는 기술이다. (원본의 "생산관리 JIT 아닌가?" → 이름만 같은 *Just-In-Time* 컴파일이 맞다. 계획을 바꾸는 AQO와는 별개 개념.)

## 7. 슬로우 쿼리 분석 순서

1. **`EXPLAIN ANALYZE`** — 실제 걸리는 시간과 실행 경로 확인
2. **예상 rows vs 실제 rows 비교** — 크게 벌어지면 옵티마이저가 낡은 통계를 보고 있다는 신호
3. **`ANALYZE` 실행** — 통계 정보 최신화
4. **인덱스 확인** — 여전히 풀스캔이면, 자주 쓰는 컬럼에 인덱스가 없는지 확인
5. **쿼리 리라이팅** — 서브쿼리를 JOIN으로 바꾸거나 다시 짜기
6. **최후의 수단으로 힌트** — 임시방편이니, 이후 다시 3~5단계로 돌아가 근본 해결

## 8. 정리

| 개념 | 한 줄 정의 |
|---|---|
| CBO | 여러 실행계획의 추정 비용을 비교해 최저 비용을 고르는 옵티마이저 |
| 통계 정보 | 옵티마이저 판단의 근거. 낡으면 계획이 틀어짐 → ANALYZE로 갱신 |
| 히스토그램 | 값의 실제 분포. 편향된 분포(99:1)에서 인덱스/풀스캔을 옳게 고르게 함 |
| EXPLAIN rows | 예상 행 수. 실제와 크게 다르면 통계가 낡았다는 신호 |
| AQO vs JIT | AQO=실행 중 계획 변경 / JIT=식을 기계어로 컴파일 (별개) |

세 줄 요약:
- 쿼리가 갑자기 느려지는 이유 → **통계·분포가 바뀌어 옵티마이저가 계획을 바꿈**
- 가장 먼저 할 일 → **예상 rows vs 실제 rows 비교 → ANALYZE**
- 힌트는 → **최후의 수단**, 통계·인덱스가 우선

<details>
<summary>답</summary>

1. 실제 실행시간이 아니라, **통계 정보에 근거한 추정 비용**.
2. 통계가 낡았는지부터 본다 — `EXPLAIN ANALYZE`로 예상 rows와 실제 rows를 비교해 크게 벌어지면 `ANALYZE`로 통계를 갱신한다.

**문제 : 같은 쿼리가 어제는 0.01초, 오늘은 30초**
- 데이터,인덱스가 그대로인데… → 원인은 옵티마이저 <br>DB가 쿼리를 실행하는 방법을 다르게 선택

**1. 옵티마이저와 비용 기반 최적화**
- 옵티마이저의 역할
	- SQL에서 원하는 데이터를 가장 빠르게 고를  수 있도록 하는 역할
		- 현대는 전부 **Cost-Based** 옵티마이저
			- 즉 비용을 추정하고 가장 낮은 걸 선택
				- 비용은 실제 실행시간이 아닌 추정치
- 추정의 근거는 통계 정보 → 통계가 오래되면 판단이 틀어진다

**통계 정보와 히스토그램**
- 통계 정보 : 옵티마이저가 참고하는 데이터 요약본
	- 테이블 행 수, 카디널리티, 히스토그램,  NULL 비율, 인덱스 선택도.
- ANALYZE 명령어
	- 데이터가 추가 혹은 지워지면 장부가 옛날 정보가 되니까 통계정보를 새롭게 업데이트 하라는 명령어
		- ANALYZE는 DB의 CPU와 메모리를 꽤 많이 쓰기에 사용자가 없는 새벽에 돌리는 게 좋다
- 히스토그램이 왜 필요하지?
	- 카디널리티가 2개일 때
		- 실제로는 각각 99% 1%의 비율로 가지고 있는데 히스토그램이 없으면?<br>아 절반씩 있겠지 하고 넘어간다
		- 이때 히스토그램이 있다면 이 비율을 정확하게 알게 된다
		- 그래서 1% 찾을 때는 인덱스를 타고 99%찾을 때는 풀스캔을 돌리는 방향으로 감

**실행계획 읽기**
- MySQL
	- `EXPLAIN` 쿼리를 날리면 결과가 표현태로 나오는데 이때 `type`, `key`, `rows`, `Extra` 를 보면 됨
		- 특히 `type` 가 중요하다
			- const, eq_ref, ref : Index Seek
			- range : Index Range Scan
			- index : 인덱스 풀스켄
			- all : 풀스캔
		- row
			- 옵티마이저가 이정도 행을 읽을거다라고 예상한 수치
			- `ANALYZE TABLE` 을 이용해서 최신화하는 것이 중요
		- `EXPLAIN ANALYZE`
			- 실제로 쿼리를 실행해서 측정한 찐 시간을 보여주는 기능
- PostgreSQL
	- 용어 매칭
		- 트리구조로 실행계획을 보여준다
		- Seq Scan : MySQL의 `ALL`
		- Index Scan : MySQL의 `ref`나 `range`
		- Bitmap Scan : 인덱스 + 풀스켄 그 사이
			- 인덱스를 뒤져서 먼저 해당되는 데이터들의 물리적 페이지 번호를 모아 메모리에 지도를 만듦→ 인덱스를 스캔하여 조건에 맞는 데이터들의 힙(Heap) 주소인 **TID를 싹 다 수집한 뒤, 이를 물리적 페이지 단위로 정렬해 메모리에 지도를 만드는 것**
			- 그걸보고 동선을 최적화 해서 디스크 헤드가 널뛰기 하는 랜덤 I/O를 줄여줌
- join 방법(전략)
	- Nested Loop (중첩 반복문)
		- A 테이블의 데이터를 한 줄씩 읽으면서, 그때마다 B 테이블을 뒤져서 짝을 맞춤
		- 소량의 데이터를 join 할 때 효과적
		- B 테이블의 조인 컬럼에 인덱스가 잘 걸려 있을 때 효과적
	- Hash Join
		- 둘 중 덩치가 작은 테이블을 통째로 메모리에 올려서 **빠른 검색용 사전을 만들어 큰 테이블을 쭉 읽으며 사전에 있는 값과 짝을 맞춤**
		- 데이터 건수가 너무 많아서 감당이 안될 때 사용(대용량 일 때 사용)
		- 인덱스가 없어도 효율적이다
	- Merge Join
		- 조인할 두 테이블을 미리 조인할 컬럼을 기준으로 각각 정렬 해둠
		- PostgreSQL이 주로 사용
	- **MySQL**
		- Nested Loop만 지원
		- 8.0.18부터 Hash Join 지원
	- **PostgreSQL**
		- 3가지 모두 지원
		- 서브쿼리 최적화
		- 정기적인 ANALYZE가 필요
- EXPLAIN (ANALYZE, BUFFERS)

**실핼 계획이 갑자기 바뀌는 이유**
- 어제는 잘 됐는데 오늘 갑자기 쿼리 속도가 많이 느려졌다면? 아래를 의심해보자
	- 통계갱신
		- 옵티마이저는 `ANALYZE`가 만들어준 '통계 장부'를 보고 길을 정함
		- 새벽에 자동으로 DB가 `ANALYZE` 를 실행한다면?
			- 통계장부가 바뀌어서 옵티마이저의 판단이 달라질 수 있다
	- 데이터 분포 변경
		- 히스토그램의 카디널리티랑 분포도 문제
		- e.g. 원래 VIP 회원이 전체회원의 1%였는데 이벤트로 인해 70%로 늘어버렸다면?
			- 옵티마이저는 Table Lookup보다 풀스켄을 선택하는 계획을 세움
	- 테이블 크기 변화
		- B-tree 타서 Clustered나 heap을 타는 건 꽤나 큰 I/O작업이다
			- 테이블이 작을 때
				- 인덱스 타는 것보다 풀스켄이 더 빠르면 풀스캔을 선택함
			- 테이블이 클 때
				- 시간이 지나 테이블이 커지면 인덱스를 타는 실행계획으로 전환함
	- 버전 업그레이드
		- BD 버전 업이 되면 옵티마이저가 새로운 알고리즘으로 실행계획을 세운다
			- DB 업그래이드 하면 기존 쿼리들이 같은 실행계획을 타는 지 테스트 하는 과정이 필요

**힌트와 쿼리 리라이팅**
- 힌트
	- 옵티마이저의 통계가 부정확할 때 강제로 이 인덱스 타라고 하는 기능
	- 쿼리 속에 주석을 넣어서 지시사항을 넣는다
		- e.g. `-- MySQL`<br>`SELECT /*+ INDEX(orders idx_user) */ * FROM orders WHERE user_id = 42;`<br>`-- PostgreSQL —`<br>`/*+ IndexScan(orders idx_user) */`<br>`SELECT * FROM orders WHERE user_id = 42;`
	- 힌트는 최후의 수단으로 둬야한다
		- 데이터가 바뀌면 힌트가 오히려 독이 됨
		- 즉, 통계 갱신(`ANALYZE`)이나 인덱스 재설계가 우선이다
- 쿼리 리라이팅
	- 결과는 같은데 쿼리를 다르게 쓰면 옵티마이저가 완전히 다른 실행 계획을 짠다는 개념
	- 서브쿼리
		- e.g. `WHERE user_id IN (...)`
			- 회원 ID를 싹 다 구한 다음 다른 테이블에서 그 ID가 있는 지 하나하나 확인하자
			- 추가 : MySQL 옵티마이저는 서브쿼리 해석 능력이 떨어짐 많이<br>그래서 바깥쪽과 안쪽 테이블을 무식하게 반복해서 빙빙 도는 최악의 실행계획을 짤 때가 많다
	- join
		- join으로 바꿔주면 hash join, merge join 같은 고급 기술을 마음껏 발휘 할 수 있다

**Adaptive Query Optimization**
- 기존 : 옵티마이저가 쿼리 실행 전 실행계획을 짠다 그래서 통계가 잘못되면 많이 느려질 수도 있다
- 적응형 쿼리 최적화 : 쿼리 도중에 막히면 실시간으로 경로를 바꿔버리는 첨단 기술
	- **Oracle 12c** : Adaptive Plan
		- Nested Loop 사용하다가 너무 느리면 Hash Join으로 바꾼다
	- **PostgreSQL**
		- JIT기술 도입!~~(이거 생산운영관리에서 나온 개념 아닌가?)~~
			- 무거운 쿼리가 돌고 있을 때 실시간으로 기계어 코드를 생성해<br>서버의 CPU 계산을 압도록으로 빨리 할 수 있도록 엔진을 부스트 해주는 기능
	- **MySQL 8.0**
		- AQO는 없다 Hash Join 추가라도 되어서 다행인 경우
